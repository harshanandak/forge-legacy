Summary

The plan in one screen

  • Forge is rebuilt as a new project, contract first, shipped as the same forge-workflow package.
  • The core is small and knows no workflow: no stages, TDD, pull requests or issues. Everything else is a block.
  • Each block declares its operations once; the command line and MCP tools are generated from that.
  • A fresh install switches nothing on. Forge reads your project and mirrors how you already work.
  • Working engines (issues, contracts, memory, flow) come over one at a time with their tests; the default is drop.
  • Our own workflow becomes one importable template among others, never part of the core.
  • Safe migration of your five projects blocks the release (a sixth, curapod, is decision 17).
  • 17 of the old plan's decisions were overturned; five need your confirmation (decisions 11 to 15).
Build order
scaffold → contract lock → 5 core lanes in parallel → first runnable slice → 9 block lanes in parallel → engines proof → delivery end to end → project migration → release
Estimate
114–170 agent-days, about 9–14 calendar weeks at 4–5 lanes at once (old plan: 92–163 days, 10–19 weeks). Estimate, not measured. Source: plan section 12.
Longest chain
34–52 agent-days of serial work, about 7–10 weeks.

Open for detail: the plan of record · review round 1 · review round 2 · the raw decision data · your rules.

Decided

Already decided by you

  • New project, same package name; the old repo is frozen to fixes and used to track the build.
  • Breaking changes are fine for a fresh 0.1.0; migrating your five projects safely blocks release.
  • Parallel lanes, each in its own worktree, each with an owner, tests and a merge point.
  • The opinionated workflow stays on top as one solution; the core never assumes it.

  • Target the latest line of each harness; no old-version shims.

1. Plain names for the building blocks

What it decides. Should the old internal names (Kernel, Contracts, Flow, Shepherd, gate, rails) be replaced by plain names people would guess?

Why it matters to you. Block names show up in config, package docs and error messages. Plain names make Forge easier to learn for you, other people and agents, but your existing notes and docs use the old words.

Example. To set up issue tracking you would configure the 'work' block, not the 'kernel' block. To check a pull request you would run 'forge pr checks', not 'forge shepherd'.

  1. Plain namesCore: block, config, template, catalog, state, host, doctor. Blocks: work (issues), memory, context, check, git, pr, github, policy, workflow, skills, project, migrate, plus one block per harness (pi, opencode, codex, claude, cursor, hermes). Kernel, Contracts, Flow, Shepherd, gate and rails stop being product words.
  2. Keep the old names as block IDsCommands still use plain nouns (forge issue claim), but the blocks are called kernel, contracts, flow and shepherd.
  3. Rename only Kernel and ShepherdKernel becomes work and Shepherd becomes pr; the other names stay.

Recommendation (default A). A. Each name says what the block owns, and 'Kernel' wrongly suggests an always-on core that also owns workflow.

What would change it. You value continuity with existing docs and memory notes more than names that are easy to guess.

Technical detail

Block IDs follow publisher/name (forge/work). Issue authority moves to forge/work; generic accepted records, events and leases stay in core 'state'; run and step records belong to forge/workflow. Source: naming-and-block-authoring.md section 4 and decisions N1/N2, with the corrected split of runs out of 'work'. The brief leaves block names open (brief.md:36).

2. Command shape

What it decides. Should commands be the short 'forge <noun> <verb>', or always include the block name?

Why it matters to you. This decides what people and agents type. Either way, Forge refuses a block that reuses a noun another block already owns, because the brief says Forge never silently replaces a choice you already made.

Example. You install a notes block that also claims the noun 'memory'. Under A, Forge refuses it and tells you to rename it in your config (for example to 'alice-notes'). Under B the clash cannot happen, because the commands are 'forge memory memory search' and 'forge alice-notes memory search'.

  1. Short commands; clashes refused'forge issue claim 42' on the command line and 'issue_claim' in MCP. A clash is refused when the block is added, and you fix it with a one-line rename in config. Install order never decides.
  2. Always include the block name'forge work issue claim 42'. Longer to type, but clashes cannot happen.

Recommendation (default A). A. It matches what your projects already type, stays short for agents, and makes every clash loud.

What would change it. Outside blocks turn out to fight over the same nouns often enough that renames become routine.

Technical detail

Operation address noun.verb with kebab segments. MCP names are noun_verb, at most 48 characters, because the Claude API forbids dots and hosts add a prefix. Reserved nouns and publishers apply. Names carry no versions: there are per-operation stability tiers and a one-minor-version 'formerly' rename window. Merges naming decisions N3, N4, N5 and N9. A 'first installed wins' option was removed: silent shadowing conflicts with brief.md:52.

3. How many Forge tools agents see through MCP

What it decides. Which Forge operations should appear directly as MCP tools in an agent's tool list?

Why it matters to you. MCP is required (the brief generates both the command line and MCP from one catalog). The open part is how much to show at once. More tools make every operation easy to reach, but they fill the agent's context and make it worse at picking the right tool.

Example. With 12 blocks installed there are about 70 operations. Under A, the agent sees up to 40 stable ones plus 3 discovery tools that can reach the rest. Under B, it sees only the 3 discovery tools and looks things up each time.

  1. Stable tools up to a budget, plus discovery toolsStable, admitted, agent-callable operations up to 40, plus catalog_list, catalog_describe and catalog_call for everything else. Human-only operations (admitting code, granting approvals) never appear. Config can pick nouns or switch to read-only.
  2. Discovery tools onlyJust catalog_list, catalog_describe and catalog_call. Smallest context, but one extra step per call.

Recommendation (default A). A. The budget keeps context cost bounded, and the discovery tools keep everything reachable through the same permission checks.

What would change it. Hosts' tool search makes large tool lists cheap (raise the budget), or measured agent runs show B is just as successful.

Technical detail

Tools are generated from the catalog record. Annotations come from declared effects (readOnlyHint, destructiveHint, idempotentHint, openWorldHint). The tools/list order is deterministic per catalog digest, with list_changed notifications. Both the pre-2026 and the 2026-07-28 stateless protocol revisions are negotiated. Pi needs exposure:'direct' for the exposed tools. Merges naming N6 and N12. A 'no MCP' option was removed because brief.md:36 requires a generated MCP surface.

4. Command-line output: machine-first or human-first

What it decides. Should Forge print JSON by default and show human-friendly text only when asked?

Why it matters to you. Agents are the main callers, and output that changes with the terminal type has broken things on Windows before. But you also use the command line yourself.

Example. 'forge issue list' prints a JSON envelope. 'forge issue list --format text' prints a table. Under B, the same command prints a table in your terminal and JSON when an agent pipes it.

  1. JSON always; text on requestOne predictable output everywhere. Add --format text for people.
  2. Detect the terminalText for a human terminal, JSON when piped, with an override flag.
  3. Text by default; --json on requestHuman-first, like most command-line tools.

Recommendation (default A). A. It keeps behaviour identical across harnesses and Windows, which was the top bug source.

What would change it. You find yourself typing --format text on most commands.

Technical detail

Envelope {ok, op, status: OK|FAIL|INCOMPLETE, result|error, warnings[]}, with exit codes 0/1/2/3/4, reconciled with the 05538ad7 regression contract. A generic renderer is used for text; there are no per-command formatters. Naming decision N7.

5. Config file format

What it decides. Should the project config stay a YAML file (.forge/config.yaml), read through one well-maintained library?

Why it matters to you. YAML is easy for people and agents to read and was already decided, but Node has no built-in YAML reader, so it costs Forge one runtime library. Node does read plain JSON, but plain JSON has no comments.

Example. Under A you edit .forge/config.yaml with comments. Under B the file is .forge/config.json with a $schema line, so editors autocomplete keys, but you cannot leave comments in it.

  1. YAML via one library behind an adapterThe 'yaml' package in strict mode: no anchors, aliases, merge keys or custom tags, with size and depth limits. Swappable later.
  2. Plain JSONRead with Node's built-in JSON parser, no library, free editor validation. No comments, and a format change from your current files.
  3. YAML with our own small parserNo library, but Forge writes and maintains a parser for the strict subset.

Recommendation (default A). A. The library has had no defects in our history, is actively maintained, sits behind one adapter so a later swap is cheap, and it keeps the decided format.

What would change it. The library gets a security advisory or a breaking major version, or you prefer a file without comments to having a library (then B).

Technical detail

Adapter config-yaml implements the ConfigParser port, with a contract suite shared by any replacement. Plan line 614 fixed YAML; dependencies-and-hooks decision Y (dependencies-and-hooks.md:208-217). JSON with comments (JSONC) is not offered as dependency-free: Node has no JSONC parser, so it would need a library or our own parser, which is option C's cost in another format.

7. Local git hook help (always opt-in)

What it decides. Forge never installs or requires a hook runner and always leaves your own hooks alone. On top of that, how much should it help when you ask for a local git hook?

Why it matters to you. Local hooks caused a dozen kinds of failure in the old Forge. Your projects that already use Lefthook, Husky or pre-commit keep them. The question is only what Forge offers when you want Forge's checks wired into a local hook.

Example. In a project that uses Lefthook, you ask Forge for a pre-push check. Under A, Forge prints the one line to add to your lefthook.yml. Under B, it can also add that line for you after showing the change, and remove it again later.

  1. Point to your hook manager; tiny hook only where none existsForge detects Lefthook, Husky, pre-commit or existing hooks and prints the line to add to them. Where no hook manager exists, 'forge hook install' writes a hook of at most 10 lines on request. Nothing is ever installed without being asked.
  2. A plus editing your hook manager's config on requestAn adapter adds or removes Forge's entry in lefthook.yml, .husky or .pre-commit-config.yaml, with a preview and a backup, only when you ask. More adapters to maintain.

Recommendation (default A). A for 0.1.0, with B filed as a follow-up. It never touches a hook manager's files, and B can be added later without changing anything else.

What would change it. Several of your projects want Forge's checks inside their existing hook manager and editing it by hand becomes a chore (then B).

Technical detail

The generated hook lives at the path from git rev-parse --git-path hooks, carries a sentinel, backs up any non-Forge hook it would replace, never sets core.hooksPath, and execs 'forge check run --trigger <event>' (catalog operation check.run with declared argument 'trigger'). Install, remove and status are catalog operations hook.install, hook.remove and hook.status in forge/git; installing writes one owned file, running the hook writes no tracked file. Behaviour tests come from #135, #382, #388, #458 and #452 (dependencies-and-hooks.md:139). Default-on and 'never offer' options were removed: brief.md:48 rules out default-on, and brief.md:52 requires an adapter offer when Forge cannot work with a user's choice.

8. An optional 'the new tests catch the bug' check in our delivery template

What it decides. Should our delivery template offer a check that the new tests fail on the old code and pass on the new code?

Why it matters to you. Your projects valued evidence that tests were written to catch the change. The brief says gates judge results, not process, so this check proves the tests catch the change; it does not prove the order they were written in. The old commit-time TDD gate is gone either way.

Example. Under B, when you switch it on, the pull request check runs the new tests against the base commit (expecting a failure) and against your head commit (expecting a pass), and reports the result. It never blocks a commit on your laptop.

  1. Results only; test-first stays adviceThe template requires tests passing on the exact commit. Test-first is guidance in the skills.
  2. Optional check, off by defaultA template rule you can switch on per project. It runs wherever your project runs its checks (usually CI on the pull request).
  3. Check on by default in the delivery templateStill applies only to projects that import the delivery template.

Recommendation (default B). B. It keeps the evidence your projects valued as an outcome you can choose, without making it the default.

What would change it. You want every project on the delivery template held to it (C), or nobody turns it on after a release (A).

Technical detail

A counterfactual regression check: a policy rule in forge/policy that uses forge/check against base and head. It replaces Product-Suite's tdd-gate hook intent and the old rail.tdd_intent. Projects without the delivery template never see it.

9. File format for blocks other people write

What it decides. Should outside block authors ship a single CommonJS file for 0.1.0, or may they also ship a modern ES module file?

Why it matters to you. The new Forge itself uses modern modules, and most TypeScript authors produce them by default. The old plan fixed a single CommonJS file because its loading and safety checks were already worked out.

Example. An author's build outputs dist/index.mjs. Under A they add one build flag to also output dist/index.cjs. Under B Forge accepts the .mjs file as is.

  1. CommonJS file for 0.1.0; modules after a proofKeep the decided single .cjs file. Add ES module entries once a test shows they load safely from the captured snapshot on Node 24/26 and Bun.
  2. Accept both from 0.1.0A .cjs or a single .mjs, both exporting the same synchronous operations.
  3. ES modules onlyDrop the CommonJS entry.

Recommendation (default A). A. It keeps a decided, safety-reviewed path for the release, and the proof needed for B is small and scheduled in the contract lane.

What would change it. The loading proof passes early in the contract lane (move to B for 0.1.0).

Technical detail

ABI trusted-action-sync/v1: module.exports.operations, a sync handler, and Promise refusal. An ESM entry would load via require(esm) or import() from the immutable snapshot; it must have no top-level await and keep the same refusal and capture semantics. Old decision 1A is kept.

10. What the first working end-to-end slice proves

What it decides. Should the first working slice prove the new building-block path with an outside block, or prove issue tracking first because your projects use it most?

Why it matters to you. The first slice sets the order of all later work. Proving the outside-block path first tests the hardest new design early. Proving issues first gives you something useful sooner.

Example. Under A, in a plain npm project, an agent's call to a small version-bump block is refused until you approve it; then it works from both the command line and MCP, with no Forge core change. Under B, the first thing that works is 'forge issue create' and 'forge issue claim' on the new state store.

  1. Outside block plus project detection firstProves the contract, generated commands, admission, a state record with a refused stale write, and detection of the project's test command, all from the packed package.
  2. Issue tracking firstPorts the issue block before the outside-block path is complete.
  3. Both in one bigger first sliceTakes longer before anything runs end to end.

Recommendation (default A). A. It catches contract mistakes before nine lanes build on them, and issue tracking follows immediately after in parallel.

What would change it. You need the new issue tracker running in your projects before the rest is ready.

Technical detail

The M2 slice in plan section 9.2: npm+vitest fixture without Bun; config show lists the detected 'npm test' with its source (detection only; running it joins at M3); an agent call before admission returns ADMISSION_REQUIRED; the human admits; semver bump returns the same result over CLI and MCP; semver.mark with a caller-supplied stale expectRevision returns REVISION_CONFLICT, plus a controlled-interleaving fixture.

11. Minimum Node version for users

What it decides. Should Forge require Node 24.15 or newer, rather than any Node 24?

Why it matters to you. Node 24.15 is where Node's built-in database reached release-candidate status, and Forge's state store uses it. It is still a release candidate, not stable, so the store stays behind an adapter either way.

Example. A user on Node 24.10 runs 'npx forge-workflow'. Under A npm warns that Node 24.15+ is required and the user upgrades within Node 24. Under B it runs on the older, experimental database build.

  1. Node 24.15 or newer, plus Node 26Matches the database's release-candidate status.
  2. Node 24.12 or newer, plus Node 26Where running TypeScript became stable; one step lower, with the database still experimental there.

Recommendation (default A). A. Users get the release-candidate database build, and the cost is a minor-version upgrade within Node 24.

What would change it. One of your projects or a known user is pinned below 24.15.

Technical detail

node:sqlite is Stability 1.2 release candidate since 24.15.0 (language-decision.md:71; dependencies-and-hooks.md:50). engines >=24.15. CI matrix Node 24 latest and Node 26. This overturns old decision 41 (existing floor) and moves it toward its option B.

12. How releases are cut and published

What it decides. Which release flow should the new repo use?

Why it matters to you. The new repo has no release automation yet. The flow decides how much ceremony each release takes and whether the published package is exactly the one that was tested.

Example. Under A, you merge a 'release 0.1.1' pull request. CI builds one package file, tests it, publishes it to the 'next' tag with a signed provenance record, installs that exact version back from npm on Node without Bun, and only then moves 'latest'. No password or token is stored.

  1. Version pull request plus automatic publishA version bump PR with a changelog generated from merged pull request titles. CI packs once, tests, publishes that exact file via npm trusted publishing with provenance, then proves the registry copy before promoting the tag.
  2. ChangesetsContributors add small change notes and a bot opens version PRs; the same publish and registry proof. Adds a development dependency.
  3. Manual publishYou run the publish yourself after CI is green; the registry proof still runs before the tag moves.

Recommendation (default A). A. It is the least ceremony that still guarantees the tested file is the published file, and it needs no new dependency.

What would change it. Outside contributors start sending many PRs that each need their own release note (then B).

Technical detail

GitHub OIDC trusted publishing with provenance. Exact-tarball BOM; registry readback of integrity, dist-tags and provenance; then a cold-cache install of the exact registry version with normal npm and Bun lifecycle, and 'npx --package forge-workflow@<version> forge' on Node without Bun (threads-ops.md:297). Unique prerelease versions on next/beta. This overturns old decision 42 (keep current automation), keeps old decision 6A (exact-artifact publication) and borrows the TanStack Config pattern.

14. Automatic re-running of failed CI checks

What it decides. Should Forge stop re-running failed CI checks on its own and leave reruns to an explicit request?

Why it matters to you. The old automatic rerun never fired or failed with errors, and rerunning until green hides real problems. But flaky infrastructure failures do waste time.

Example. A pull request check fails with a runner network timeout. Under A, 'forge pr status' reports it as an infrastructure failure, and the agent calls 'forge pr rerun' with that evidence. Under B, Forge reruns it once by itself.

  1. No automatic rerunsAn explicit rerun operation that records the evidence for why. Repeated failures are quarantined with an issue.
  2. One bounded automatic rerun for infrastructure failuresThe old default: only for clearly classified infrastructure failures, bound to the exact commit.

Recommendation (default A). A. It removes a feature that never worked reliably, and agents can rerun deliberately with evidence.

What would change it. Infrastructure flakes turn out to cost more agent time than the explicit rerun saves.

Technical detail

This overturns old decision 40A. pr.rerun has effects external:github and a required reason/evidence input. The auto-actions Tier-A path is dropped (threads-ops lesson 6).

15. Mutation testing in our repo

What it decides. Should our new repo drop the mutation-testing tool and instead prove critical fixes with targeted 'remove the fix, the test must fail' checks?

Why it matters to you. You had decided to keep a mutation-testing lane. The tool is heavy, needed a disruptive upgrade, and was never fully working, while the fixes that matter most are a short list of race and authority bugs. This concerns only how we test Forge, not users' projects.

Example. For the expired-lease fix, CI temporarily removes the fix line and confirms the regression test now fails. Under B, a mutation tool also mutates the whole codebase in a separate job.

  1. Targeted remove-the-fix checks onlyFor every authority, concurrency and gate fix. No mutation tool.
  2. Keep a mutation-testing job in CIOptional job, with the same targeted checks on top.

Recommendation (default A). A. It proves exactly the tests that guard the costly bugs, without the heavy tool.

What would change it. Coverage gaps keep letting regressions through in code that has no targeted check.

Technical detail

This overturns owner-decided old decision 5A (retain the configured mutation lane). Stryker DROP (dependencies-and-hooks b3); mistakes-ledger rule 7.

18. What to do with the old Forge backlog

19. How many lanes run at once

What it decides. How many parallel work lanes should run at the same time after the core design is locked?

Why it matters to you. More lanes finish sooner but need more of your review time and cause more merge conflicts in shared files. Fewer lanes are calmer but take longer. This is a staffing guess, not a delivery date.

Example. Under A, about 4-5 lanes run at once and the estimate is about 9-14 weeks. Under B, 3 lanes run and it is about 10-15 weeks, with fewer reviews landing at the same time.

  1. 4-5 lanes at onceUp to 9 lanes are startable after the first working slice; at most 3 merges queue at a time.
  2. 3 lanes at onceSlower, lighter on your review time.
  3. 6 or more lanes at onceFastest on paper; review and conflicts become the limit.

Recommendation (default A). A. The critical path limits the gain beyond 5 lanes, and shared-file conflicts stay manageable with single owners.

What would change it. You can give less than about 15 focused hours a week to reviews and approvals (then B).

Technical detail

Critical path from the section 12 earliest-start table: L0, L1, L5, M2, M3 (L7/L8/L11 plus integration), L14 converter, L14 cutover, L15 tail, about 34-52 agent-days. Throughput is about 5 agent-days per lane per week, so the calendar is max(path, throughput) + 2-3 weeks. Conflict hot spots are migrations/state driver, schemas and ports, package.json/exports, and the assembly list, each single-owner.
