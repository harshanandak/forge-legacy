### 1.2 Codex: what Forge should NOT build

1. **Instruction loading, skill discovery and skill invocation.** Codex reads `AGENTS.md` (nested root-to-cwd) and `.agents/skills` natively, with `allow_implicit_invocation` as the exact analogue of Forge's `invocation: user|model`. Forge writes one canonical `.agents/skills`; it does not need a Codex-specific skills mirror. [read C2, C3]
2. **Sandbox, approvals, auto-review, command rules.** Seatbelt/bubblewrap/Windows sandbox, `approval_policy`, `.rules`, and the Starlark `execpolicy`. Forge should not ship its own process sandbox or command allow-list engine for Codex. [read C10, C13, C18]
3. **Session driving, resume/fork, worktrees, headless runner, structured final output.** `codex exec --json --output-schema -o`, `exec resume/fork`, `--worktree`, app-server and SDKs. Forge must not build a Codex runner or session store (plan §3.5 already says this). [read C6, C12, C14, C15]
4. (Also native) MCP client with OAuth, subagent orchestration with `[agents]` limits, `/plan`, plugin marketplaces and installers. Distribute through a marketplace rather than writing an installer.

### 1.3 Codex: what Forge must supply

1. **A portable plugin + marketplace entry** (`plugin.json` + `skills/` + `mcp.json` + `hooks/hooks.json`) published through `.agents/plugins/marketplace.json` (git/npm source), plus the **trust handshake**: hooks are inert until the user runs `/hooks` trust, so Forge cannot assume a written hook is active (`written-is-not-active`). The plan's L2 proof must exercise a real trusted run. [read C1, C5; plan §3.5]
2. **Shared run/issue authority behind hooks and MCP.** Codex hooks can deny a tool call but the docs call them "not a complete enforcement boundary" and omit hosted tools, so Forge's gates must stay in the Kernel/CLI/git/CI; the hook is a thin client that calls the Kernel and returns allow/deny. [read C1; inferred]
3. **Cross-harness handoff and evidence.** Codex memory is per-machine, generated, off by default and not authoritative; resume state lives in `~/.codex`. Forge must provide the portable handoff record (issue/run id, evidence, next step) that a Pi or OpenCode session can read, instead of relying on Codex memory or transcripts. [read C11; inferred]
4. **Config projection:** `.codex/config.toml` (`[mcp_servers.forge]`, `[plugins."forge@..."]`, `[features]`), `.codex/agents/*.toml` if wanted, and the profile-file model (not `[profiles]`). Respect project trust: untrusted projects skip all `.codex/` layers, so the projection must detect and report that. [read C8, C9]
5. **Contracts for `--output-schema` results** (Forge's schemas converted to the Codex JSON-Schema subset, `additionalProperties:false`) so `codex exec` output maps to Forge evidence. [read C6; inferred]

### 1.4 Codex: unclear / needs a real run before relying on it

- Whether `codex exec` runs hooks and whether plugin-bundled hooks load in CLI (C5 says "manually installed Codex desktop plugins").
- Exit-code table for `codex exec`.
- MCP tool-name sanitising rules; AGENTS.md/skills resolution inside linked worktrees; protected-path rules in the sandbox.
- `$CODEX_HOME/skills` support status (docs table omits it).

## 2. OpenCode (two lines: V1 1.19.3 and V2 2.0.31)

**Critical finding.** OpenCode now ships two incompatible lines under the same `opencode` command. The default installer on opencode.ai now points to V2 (`opencode.ai/v2/install`, `opencode-v2` brew formula, Docker `2.0.0`), while npm `opencode-ai@latest` is still 1.19.3 and 1.19.0 added `opencode upgrade --major` to move to V2. Config key names differ (`permission`/`bash`/`task` in V1 vs `permissions`/`shell`/`subagent` in V2), the plugin APIs share nothing, and V2 docs do not say whether V2 is stable or beta (the AUR package is `opencode-beta`). [read O1, O16, O21; ran npm/gh]. The plan's "stable, TUI and v2 are distinct families" (plan §3.5) is confirmed and sharpened. A plugin object can carry both entry points (V2 `setup()` plus V1 `server()`; V2 ignores `server()` and vice versa; V1 object form supported from 1.18.29) [read O18].

### 2.2 OpenCode: what Forge should NOT build

[read O6, O9]
2. **Server/SDK/session machinery.** `opencode serve` + OpenAPI + SSE + `@opencode-ai/sdk` already give headless driving, forking, aborts, permission replies, and JSON-schema structured output. Forge must not build an OpenCode runner. [read O11, O15]
3. **Agents, subagents, plan mode, permissions DSL, provider policies, MCP client with OAuth.** All native. Use agent frontmatter + `permission`/`permissions` for read-only reviewer agents rather than a Forge permission engine. [read O3, O8, O13, O7]

### 2.3 OpenCode: what Forge must supply

1. **Real enforcement outside the harness.** There is no OS sandbox in either line, and V1 defaults are mostly `allow`. A Forge plugin can throw in `tool.execute.before` (V1) or set `deny` in `permission evaluate` (V2), but plugins run in-process, can be bypassed by `--auto` for anything not explicitly denied, and `OPENCODE_PERMISSION`/`OPENCODE_CONFIG_CONTENT` can override config. Gates must therefore stay in the Kernel, git hooks, and CI; the OpenCode plugin is a client that fails closed when Forge is unreachable ("load-failed governance refuses promised operations", plan §3.5). [read O2, O10, O21; inferred]
2. **Two plugin entry points** (V1 `server()` and V2 `Plugin.define({id,setup})` in one package, per O18) plus per-line proof. Forge must pin which line each support record covers, and generate permission config in the right dialect (`bash` vs `shell`, `task` vs `subagent`, `permission` vs `permissions`). [read O18, O21]
3. **Config projection:** `opencode.json(c)` entries (`mcp.forge`, `plugin(s)`, `instructions`, agent definitions), `.opencode/commands|agents|skills`, with the merge order above; and detection of managed config that outranks the projection.
4. **Cross-harness handoff + evidence**, same reason as Codex: OpenCode sessions live in its DB; the portable record must live in Forge.
5. **Distribution:** no marketplace exists, so Forge ships an npm package (plugin) and writes the `plugin` entry; installs run Bun and execute arbitrary package code (trust note for the owner's consent flow).

### 3.3 Pi: what Forge must supply
