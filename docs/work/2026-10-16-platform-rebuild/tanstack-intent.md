# TanStack Intent — what it is and where it fits Forge

Research date 2026-10-16. Read-only; the only side effects were `npm view`/`curl`/`gh api` GETs. Markers: **read** (URL, fetched 2026-10-16), **ran** (command), **inferred**.

## 1. What it is

**TanStack Intent exists and is what the owner likely means.** It is a CLI, `@tanstack/intent`, for shipping and consuming *Agent Skills* inside npm packages. A library ships `skills/<name>/SKILL.md` files in its tarball; a consumer's tool discovers them from installed dependencies. The skills are versioned with the package. The problem it targets is the "lifecycle" gap: agents get library usage wrong because the knowledge isn't delivered through a channel the maintainer controls (stale community rules, training data mixing versions). (read: https://tanstack.com/blog/from-docs-to-agents, "Introducing TanStack Intent", published 2026-03-04, Sarah Gerrard and Kyle Mathews.)

### How it works

- **Skill format.** It is the open Agent Skills format (agentskills.io): a directory with `SKILL.md`, YAML frontmatter and optional `scripts/`, `references/`, `assets/`. The spec requires `name` (max 64 chars, lowercase/digits/hyphens, must match the directory) and `description` (max 1024). It allows `license`, `compatibility`, `metadata` (string map) and experimental `allowed-tools`. It uses progressive disclosure: ~100 tokens of metadata at startup, the body on activation, resources on demand (read: https://agentskills.io/specification). Intent's validator adds top-level `sources` and `requires` arrays, a 500-line cap per file, and requires `metadata.library_version`-style fields to live under `metadata` (read: docs/cli/intent-validate.md in the repo, via `gh api`).
- **Shipping (maintainer).** `skills/` goes in the tarball and the package carries the keyword `tanstack-intent`. `intent maintainer sync` adds the keyword and the `files` entries; `maintainer setup/add/status/review/check`, `meta generate-skill`, `validate [--fix|--check|--set-version]`, `stale` and `repair` cover authoring and maintenance. Authoring is done by "your existing coding agent" following Intent's meta-skills, and review evidence is recorded in `.intent/` (read: docs/overview.md, docs/registry.md, docs/cli/*).
- **Consuming.** `intent list` scans `node_modules`, workspace packages and Yarn PnP and does not execute package code. `intent load <pkg>#<skill> [--json|--path]` prints the `SKILL.md` for the installed version. `intent install` writes a managed `intent-skills` block into `AGENTS.md` (default), `CLAUDE.md`, `.cursorrules` or `.github/copilot-instructions.md`, telling the agent to run `intent list`/`intent load` before editing; `--map` writes explicit task→skill mappings (read: docs/overview.md, docs/cli/intent-install.md).
- **Hooks (opt-in).** `intent hooks install` adds a `SessionStart` skill catalog and a `PreToolUse` **edit gate** that blocks edits until the agent has run `intent list`/`load`. Project scope covers Claude Code (`.claude/settings.json`) and Codex (`.codex/hooks.json`); Copilot CLI hooks are user-scope only; Cursor and generic AGENTS.md agents get guidance only. The docs state the hook does not prove the skill matched or was applied (read: docs/cli/intent-hooks.md).
- **Trust.** `package.json#intent.skills` is an allowlist and `intent.exclude` a blocklist. Discovery includes transitive dependencies, and trust does not propagate. **Without an allowlist every discovered package is surfaced, with a deprecation notice; a future version will require one.** Enabling a source does not approve its specific instructions: "Skill content can change when dependencies update, and Intent does not yet track or notify you about those changes." The `git:` source kind is reserved and rejected (read: docs/concepts/trust-model.md, configuration.md).
- **Registry.** tanstack.com/intent/registry periodically searches npm for the `tanstack-intent` keyword, downloads the tarball and indexes every `skills/**/SKILL.md`. There is no submission step (read: docs/registry.md).
- **Harnesses.** *Harness support is thin and is not skill projection.* Intent does not write per-harness skill directories (no doc says it does; **inferred** from the docs listing only AGENTS.md-family guidance files and the hooks above). The launch post names the Agent Skills adopters (VS Code, Copilot, Codex, Cursor, Claude Code, Goose, Amp) but that is about the spec, not Intent features.
- **Maturity signals.** The post gives no benchmarks and calls the rollout early (read: blog). `validate --fix` exists to migrate frontmatter written by earlier Intent versions, e.g. moving `type`/`library`/`library_version` under `metadata`, so the format has already churned. First-run `install` needs a TTY and fails non-interactively (read: docs/concepts/trust-model.md, quick-start-consumers.md). `maintainer setup` writes planning records and AGENTS.md blocks into the library repo.

**Not found / unverified:** a stable 1.0 roadmap; any measured effect on agent accuracy; a published JSON schema for the CLI's `--json` outputs beyond the `load --json` example; whether Claude Code or Codex natively read `node_modules/*/skills` (not claimed here).

## 2. Where it could fit Forge

Forge facts used: the `skills` block owns the `skill` noun (`list/show/find`); Contracts catalogs Agent Skills and adapters emit them, with no loader per host; skills name operations as `noun.verb` and a conformance check fails the build on unknown operations; `packages/skills` deps (chalk, commander, inquirer, js-yaml, markdown-it) are all DROP or REPLACE (read: naming-and-block-authoring.md:279,418; architecture-evaluation.md:86,105; dependencies-and-hooks.md:43-47).

|---|---|---|---|---|---|
| 1 | **Block packages ship skills in the standard layout** (`skills/<name>/SKILL.md`, agentskills.io-valid; optionally also the `tanstack-intent` keyword) | Adds a distribution path for block-authored skills that needs no Forge-specific channel. It matches the "blocks anyone can add" goal: the block package carries its own agent knowledge, versioned with its operations. | Near zero. It is a layout convention plus one `package.json` keyword. | The keyword brands the package as TanStack-tooling-compatible and Intent's tarball expectations may shift (alpha). The spec layout itself is neutral and stable. | **Convention we stay compatible with.** |
| 2 | **Skill discovery by agents from installed blocks** | The `skills` block scans installed block packages for `skills/**/SKILL.md` and serves `skill.list/show/find` from the generated catalog (CLI and MCP). Intent's `list/load` solve the same problem but through their own CLI and guidance block. | A native static scanner is small (read directory, parse a fenced frontmatter block; dependencies-and-hooks.md:47 already plans to do this without a Markdown engine). ### Why not a core dependency

- **Maturity:** alpha, 0.x, five minors in four months, an existing frontmatter migration path, and a stated upcoming breaking change (mandatory allowlist). That fails "build for stable, not for today's gaps".
- **Dependency budget:** 0.5.5 has no runtime dependencies (inferred from the empty `dependencies` field), so the install cost is low. The real cost is **surface**: a second CLI, a second set of names, managed blocks in AGENTS.md/CLAUDE.md, and TTY-only first-run setup (an agent cannot answer it).
- **Lock-in:** low for the file format, because it is the open Agent Skills layout. Higher for the workflow (`.intent/` records, managed guidance blocks, the `intent load` indirection).
- **Opinionated flow leak:** Intent's edit gate is a process gate. Nothing in Forge core may depend on it.
- **Single owner of trust and discovery:** Forge's catalog and trust policy own these. A second authority would reintroduce the "generated harness files reference things that don't exist" failure (ledger:77, as cited in naming-and-block-authoring.md:279).

## 3. Recommendation

- **A. Convention + native reader (default).** Block packages ship `skills/<name>/SKILL.md` in the agentskills.io layout. The `skills` block discovers them statically from installed packages (never executing package code) and serves them through the generated catalog. Block-author docs say "Intent-compatible; the `tanstack-intent` keyword is optional", plus an optional `intent validate`/`stale` recipe. No dependency.
- **B. A plus an optional `skills-source-intent` adapter.** It is detected automatically when the project already uses Intent and delegates to `intent list/load --json`. Build it only if a real user asks.
- **C. Core dependency on `@tanstack/intent`.** Not recommended.
- **D. Ignore it.** Viable but loses cheap interoperability: with ~177k weekly downloads it is becoming the de-facto way libraries ship skills, so stay layout-compatible.

**Default: A.** Reasons: it captures fits 1, 2 and 5 (the real value, which is a standard place for blocks to carry agent-facing knowledge) at close to zero cost. It keeps Forge's catalog as the single naming, discovery and trust authority. The open skill layout is the stable part, while Intent's CLI and maintainer workflow are the unstable part and stay optional.

**What would change it:**
- To **B**: users arrive with Intent already installed and want Forge to read their allowlist or skills; or Intent publishes a stable, versioned `--json` contract.
- To **C**: Intent reaches 1.0 with documented format and CLI stability, an enforced allowlist, content pinning/change notification, a non-interactive install, and the `skills` block would otherwise re-implement most of its discovery. Even then it would be an adapter, not core.
- To **D**: Intent's format diverges from agentskills.io, or the project stalls (it was last pushed 2026-10-07 with active maintainers, so no sign of this today).
- Away from the native reader: Claude Code, Codex and other harnesses start loading `node_modules/*/skills` natively. Forge's adapters would then only need to expose the packages' skills, not copy them (not verified; **inferred** as the direction of travel).
