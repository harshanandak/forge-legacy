## Where the opinionated flow leaks into core (brief rule) [read]

1. **The command registry enforces stages.** `lib/commands/_registry.js:14` imports `workflow/stages`. `:237-252` runs `enforceStage` for any stage-named command. `:311-316` writes stage completion into the Kernel when a command succeeds. Every solution built on the blocks would inherit Forge's stage ladder. New rule: the registry knows only commands and contracts. A solution registers its own pre/post hooks.
2. **`bin/forge.js:81-82, 3800, 3873-3880`** applies `enforceStageEntry` to any command whose name is a stage, and rewrites `pr ship` into the bare stage path.
3. **The config resolver's gate defaults carry stage phases and artifacts.** `lib/core/runtime-graph.js:67` declares `Gate({id, phase, …})`, and `:404, :410` require `artifact.design-doc`, `artifact.task-list` and `evidence.tdd-tests`. The project config template also hard-codes the flow: Product-Suite and Zwapit `.forge/config.yaml` both carry `workflow.phases`, `gates`, `classification` and "Default Forge command flow" [ran: key census]. New rule: the config schema has generic capability bindings, and phases exist only inside the delivery template.
4. **The issue surface depends on stages.** `lib/commands/_issue.js` imports `workflow/stage-transition` [read: require census]. A Kernel comment must not parse stage-exit text.
5. **Delivery side effects are wired into generic verbs.** push.js, ship.js and hooks.js require `pr-monitor/reconcile-executor` to wake the shepherd daemon [read: require census]. Under 39A that wake disappears. Any wake-up must be an explicit solution hook, never part of `push`.
6. **Health checks are keyed to stage entry.** `lib/runtime-health.js` is described as "Runtime prerequisite checks for stage entry" [read: line 1 comment]. It becomes neutral `doctor` checks.
7. **`activation/ensure-forge-home.isMutatingVerb`** is keyed on command names. It has to come from per-command contract metadata (`effects: write`) instead.

## Parallel lanes vs serialized work [read: require census; inferred]

**Shared files that must be serialized:**

- **CLI skeleton first, alone:** the new `bin/forge.js`, command registry, `global-flags`, `_resolve-command-opts` and JSON envelope. Every command lane builds against it. Do **not** port the static `_manifest.js`: a generated manifest edited by every lane becomes a merge hotspot. Instead, have each lane add one self-describing command file, and generate the manifest in CI or at pack time.
- **Issue surface:** `_issue.js` is behind all 17 issue/standalone-verb files. One lane, after the Kernel-lane client contract.
- **Delivery PR cluster:** `pr.js` requires `merge`, `ship`, `shepherd` and `preflight`. `github.js` requires `merge`. `shepherd.js` requires `ship`. merge, shepherd, pr, ship, pr-pull, pr-bundle, pr-shepherd and pr-monitor go in one lane, or strictly in order: merge-rules → merge → pr link → ship → shepherd.
- **Native-host cluster:** `setup.js` pulls about 35 libs, which overlap with `hooks.js` (hook-renderer, hook-global-installer, using-forge, memory-*). One lane: native profile writer → setup → hooks.
- **push + validate + test** share `validation-receipt`, `shell-utils` and `scripts/test`. One lane.

**Can run in parallel once the skeleton exists:**

- Worktree lane: worktree, clean, detect-worktree, modules-link, git-defaults.
- GitHub routing lane: github, gh-proxy, github-router, github-context, github-credential, native-gh, plus the two bin shims.
- Preflight + doc-gate lane.
- Memory CLI lane: remember, recall, memory, project-memory, memory-recall/digest/events. Waits on the Memory engine lane.
- Kernel extras lane: export, doctor, migrate converter. migrate waits on the Kernel target format freeze.
- Config verbs lane: options, explain, control, role, add, audit, gate → `config`. Waits on the Contracts config-writer contract.

## Top risks

1. **The stage-coupled registry gets ported "as is".** `_registry.js` and `bin/forge.js` are the first files any lane touches, and they hard-wire stage enforcement and completion recording (leaks 1–2). Copying them would lock the delivery flow into core on day one. Mitigation: rewrite the skeleton first, with a test showing that a second solution can register commands that carry no stage semantics.
2. **Hard-won delivery fixes get lost in ADAPT.** merge (7 fixes with tests), validate (18 fix commits), worktree (12), clean (5), push (4), preflight (3) and pr-pull (6) carry the bulk of the regression knowledge. Reshaping their APIs without bringing the named regression tests along (merge-authority*.test.js, validate.test.js, worktree*.test.js, clean.test.js, shepherd-merge-safety.test.js, preflight/gates/runner tests) would reintroduce false-clean merges, fail-open gates and lost worktrees. Mitigation: each lane's acceptance list is the "hard-won fixes" column, rewritten as behaviour tests against the new contract.
3. **The five-project migration surface is wider than the issue verbs.** Product-Suite runs live `forge hooks session-start|capture|inbox-pickup|shepherd-events`, two native-hook intents and a phase-bearing `.forge/config.yaml`. It also holds daemon-era tables (memory_monitor_* 442 rows each, kernel_pr_watch_owners 10), pins `^0.0.9`, and depends on per-user `~/.forge/github-router-clones.json` and `validation-receipt.key`. Dropped hooks or unread tables would break it silently. Mitigation: the converter's acceptance includes a hook-command census per project, and Decision C.

Smaller risks: the `scripts/` dependency from push/skill is in no lane. Some `fix` commits touch tests only incidentally, so their "regression test" mark is rung 1 until the test assertion is read. User-global hook wiring is unknown (see the five-projects section).
