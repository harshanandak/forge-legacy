# P5: Complement, don't compete; the current OpenAI/ChatGPT developer platform; build versus adopt

Leg P5 of the Forge final-plan research. Brief: (local scratch). Rules: (local scratch). Audited plan: [platform-plan-final.md](platform-plan-final.md) ("the plan"; line refs are `plan:L<n>` in the worktree checkout of origin/master). North star: [north-star.md](../north-star.md) ("N").

## Bottom line

1. **The plan has one real overlap problem, not five.** Admission, identity, authority, gates, the config compiler and the Vercel/LangGraph/MCP facades are complements. The overlap is the **executable composition runtime**: the 32-node/256-edge DAG binder with Kernel-connected resume (plan:L499-518). LangGraph, Mastra workflows, CrewAI Flows and AI SDK 7's `WorkflowAgent` and Workflow SDK all own that layer. Verdict: **NARROW**. [read; external]
2. **Memory overlaps on the agent-memory side only.** Mastra, LangGraph stores, Agents SDK sessions, Mem0 and Graphiti own conversation and semantic memory. Forge Memory should be positioned as project/decision memory with provenance tied to Kernel identities. External engines plug in as enrichment providers; Forge already has a Graphiti MCP descriptor (lib/memory/graphiti-mcp.js:1-22). Verdict: **NARROW + ADAPTER OPTION**. [read; external]
3. **New overlap the plan doesn't name: harness invocation.** AI SDK 7 now ships `HarnessAgent` adapters for Claude Code, Codex, Cursor, OpenCode, Copilot and others. T3 Code and Codex App Server also drive harness sessions. Forge's harness adapter should **project and certify** (plugins, skills, MCP, hooks) and never drive sessions. The "native discovery/invocation" verb in plan:L534 should narrow to "conformance transcript". [external]
4. **Positioning (one sentence):** *Forge is the verifiable building-block layer that agent runtimes and harnesses plug in: admitted, authority-backed capabilities (issue/workflow authority, project memory with provenance, gates, guarded delivery), delivered in each host's native extension format. Forge never runs models, owns an agent loop or acts as a durable workflow engine.* [inferred]
5. **OpenAI DevDay 2026 was September 29, 2026** (confirmed). Plugins are now one bundle (MCP server + skills + optional UI) in a **single plugin directory shared by ChatGPT and Codex**. Plugin Extensions (sidebar apps, conversation panels, file viewers, composer mentions) sit on top of MCP Apps. MCP Events (beta, webhook delivery) and the Agents API (public beta, the Codex harness as an API) are also new, and Agent Builder shuts down on **November 30, 2026**. [external]
6. **Cross-vendor packaging now exists:** Codex plugins use the vendor-neutral **Agent Plugins** `plugin.json` (TSC: Amazon, Cursor, Microsoft, OpenAI, Vercel), and skills follow the **Agent Skills** spec, which Claude Code, Codex, Cursor, OpenCode and Hermes all list. Forge should emit these formats, not invent its own projection format. Verdict: **ADOPT AS BLOCK (formats)**. [external]
7. **0.1.0 OpenAI scope (cheap, high exposure):** a **Codex plugin**, meaning an Agent Plugins `plugin.json` plus canonical `.agents/skills` plus `mcp.json` pointing at the already-planned same-package stdio MCP server, plus a repo marketplace file. Est. **2-4 worker-days** on top of the stdio MCP work. [inferred]
8. **ChatGPT app/plugin (MCP Apps UI, sidebar, MCP Events) is 0.2+.** ChatGPT developer mode accepts only SSE/streaming HTTP MCP with OAuth/CIMD or no-auth. Forge state is a local SQLite Kernel, so a ChatGPT surface needs the remote/auth/cloud seams that §3.8/§3.10 already stage after 0.1.0. Putting it in 0.1.0 would pull hosted auth onto the critical path. [external; inferred]
9. **The plan's MCP profile needs a spec update:** MCP **2026-07-28** (GA July 28, 2026) removes `initialize`, adds `server/discover`, formalizes extensions, and is required by ChatGPT MCP Events. Plan:L554 still says clients "initialize, list, call and close". Pin and test the protocol version explicitly. [external; read]
10. **Build vs adopt across 14 blocks:**
    - KEEP NATIVE (4): Kernel authority, protected gates, config compiler, open conformance checker.
    - ADOPT AS BLOCK (3, formats/standards): skills/plugin packaging, supply-chain attestations, event/trace export.
    - ADAPTER OPTION (7): Memory engines, durable execution, review providers, merge queue, cloud backup, issue-tracker projections, release tooling.
    - Biggest maintenance lever: the ~8.3k-line PR-monitor/shepherd stack versus GitHub merge queue plus required checks. This needs its own scoped comparison, not a silent cut. [ran: line counts; inferred]

**Decisions needed:** the 5 open questions at the end (defaults stated). Nothing here authorizes implementation.

### A2. What T3 Code owns, and the complement principle

T3 Code describes itself as an "agent harness control surface" (desktop, web, mobile). It supports Codex, Claude Code, Cursor, Grok Build, OpenCode and Google Antigravity, each "via" the provider's own CLI or auth. Users must "install and authenticate at least one provider before use". License MIT; "very very early". [external: [t3code README](https://github.com/pingdotgg/t3code)] Codex's own rich-client surface is the **Codex App Server** (JSON-RPC 2.0 over stdio by default; `thread/*`, `turn/*`, `item/permissions/requestApproval`, streamed `item/*` events). A GUI like T3 Code can embed it. [external: [App Server](https://learn.chatgpt.com/docs/app-server)]

**The complement principle, extracted [inferred]:**
1. **Consume the host's own runtime through its official seam.** T3 Code uses the provider's CLI, auth and app-server. It never reimplements the agent loop, tools or session state.
2. **Own a layer the host lacks.** For T3 Code that's the multi-harness control surface. For Forge it's verifiable capabilities and work authority.
3. **Degrade to the host.** If T3 Code disappears, the harness still works. If Forge disappears, the user's LangGraph/Mastra/Claude Code setup keeps running and only loses Forge tools/guards.
4. **Speak the host's extension format,** not a Forge-specific one.

**Test for any Forge capability:** "Would a user of runtime X have to stop using X's equivalent feature to use this?" If yes, it's OVERLAP.

### A4. Disposition of every OVERLAP

| Overlap | Verdict | What changes, why, what's rejected, what would change it |
| --- | --- | --- |
| **Flow DAG binder + Kernel-connected resume** (plan:L499-518, L986, L1019) | **NARROW** | **Keep:** single-operation invocation through admission/wrapper/evidence; config compile/explain of a composition graph (validation, effects, grants), which is a complement; sequential execution **only for Forge's own reference template and headless CI**, where the Kernel is already the authority. **Delegate:** for any framework consumer, one Forge operation = one tool call or one workflow step. Retries, branching, durable timers, human-interrupt resume and parallelism stay with LangGraph/Mastra/Workflow SDK. **Shrink proof:** the 256-edge/32-node packed campaign certifies a general graph runtime few outside users will choose over their framework's. Cap the public executable graph at what the reference template needs, measured, and keep the larger compile/explain limits for validation. **Rejected:** (a) KEEP as is: it competes with every SDK on their home turf with weaker features (no loops, no parallelism, no interrupts) [inferred]; (b) DELEGATE fully, e.g. making the reference template run on LangGraph: this would add a mandatory third-party runtime dependency to the one Forge package and break agent-first headless use. **Would change it:** pilot users (decision 16) composing multi-node graphs in Forge rather than in their framework, or a framework adapter failing to preserve Forge refusals. |
| **Memory** (plan:L301, L314-353, L985) | **NARROW + ADAPTER OPTION** | **Keep:** local, provenance-bearing project/decision notes bound to Kernel IDs, exportable and forgettable (the "local floor"). **Position:** project memory for work, not conversational memory. **Delegate:** chat history, semantic recall and user profiles stay with the runtime (Mastra memory, LangGraph store, Agents SDK sessions). **Offer:** Mem0 and Graphiti as enrichment providers behind the existing registry (Graphiti precedent: lib/memory/graphiti-mcp.js). Later, expose Forge Memory **outward** as a memory provider (Mastra storage/memory-processor seam, LangGraph custom store) so the complement direction runs both ways. **Rejected:** a vector store or semantic-recall engine in core. **Would change it:** repeated pilot demand for semantic recall that no adapter serves. |

Forge doesn't drive sessions; T3 Code, AI SDK `HarnessAgent` and Codex App Server do. For headless harness runs, document `HarnessAgent` + Forge tools rather than building a runner. **Would change it:** a certified host that offers no non-interactive run path at all. |
| **Marketplace distribution** (plan:L577-595) | **NARROW** | **Keep:** identity records, exact-release locks, review tiers, the open checker and a **static generated index** that points at npm artifacts. **Delegate distribution** to the host directories: OpenAI plugin directory (ChatGPT+Codex), Claude marketplaces, Cursor plugins, MCP Registry. Forge's guarded create/link/refuse/cleanup is reference-required and safety-critical; keep it, but expose it as a tool and never require it when the host already isolates. |

**Forge never does (list for docs and review checklists) [inferred]:**
1. Call a model or abstract model providers.
2. Run an agent or tool-calling loop.
3. Provide durable workflow orchestration for external solutions: no timers, retries-as-graph, interrupts/HITL resume, parallel scheduling or long-running jobs.
4. Store conversation history or provide semantic/vector recall as a core engine.
5. Stream chat UI or ship a chat frontend.
6. Drive harness sessions as a client (spawn/steer Claude Code, Codex or Cursor turns).
7. Host agent deployments or offer an evals platform.
8. Become a second issue authority, or invent a packaging format where a cross-vendor one exists.
