# Decisions 1-14 in plain language

## 1. What kind of code outside authors can plug into Forge at launch
Status: open (default A)
**What this decides:** When someone outside the project writes a "block" (a plug-in capability) for Forge 0.1.0, what is that code allowed to do when Forge runs it?
**Why it matters to you:** This sets what "anyone can add a capability" actually means at launch, which is the north-star promise.
**Example:** Someone writes a "release-notes advisor" that takes a list of changed APIs and returns advice. Under A it works: data in, answer out, immediately. Someone else writes a "post to Slack" or "look up the customer in the CRM" block. Under A it cannot be an outside block, because calling a web API is asynchronous (it waits on the network) and A rejects any block that returns a promise. The agent or a Forge built-in has to make that call instead.
**Options:**
- **A — Quick answer-only blocks:** outside code gets data and returns a result at once, with no waiting on the network, no background work and no long-running process. It's simple and safe enough for trusted local code, but most real integrations can't be outside blocks yet. Not costed separately.
- **B — Also allow long-running or stateful services:** blocks can start, keep state, wait on networks and shut down. Forge then has to manage start, stop, crashes and cleanup. Not costed in the plan.
- **C — Sandbox all outside code before release:** run it in an isolated process or container with security proof. It's the safest option, but it pushes the release date and isn't costed.
**Recommendation:** A, but note there's a gap the plan doesn't offer: "allow one-shot async calls (wait for one network request, with a timeout), still no long-running services." That would cover most integrations. A pure answer-only rule will look restrictive as agents get more capable.
**What would change this:** If the first outside authors' real blocks mostly need network calls, move to that middle option or B.

## 2. Package name and version for launch
Status: decided (A)
**What this decides:** What npm name and version number the new platform ships under.
**Chosen:** keep the existing `forge-workflow` name and launch as 0.1.0, retiring the old 0.0.x test line. Test builds go out only on beta/next tags, never as the default install.

## 3. How much proof is needed before launch
Status: decided (A)
**What this decides:** How much testing the first public release needs.
**Chosen:** the lighter experimental launch: full CI on every platform, an install test of the packed package, an outside author proving they can build a block in two agent tools, and safe migration of all five of your personal projects with no data loss. The seven-day observation period, 50-journey campaign and release-candidate ritual are dropped.

## 4. How big the build is and how long it takes
Status: open (default C)
**What this decides:** Which work estimate to plan against: the full scope, a smaller scope with named cuts, or no estimate until you measure your real capacity.
**Why it matters to you:** You are the only maintainer. The estimate decides what gets built before launch and how many weeks of your evenings it eats.
**Example:** Under C, support for the T3 host, a new native Hermes package, demo integrations with outside memory providers, a Vercel adapter, an extra compiled-Bun experiment and extra Claude/Cursor polish are cut from launch. Under A they stay in and the estimate grows. Under B you first track a few weeks of actual throughput before picking any range.
**Options:**
- **A — Keep the full corrected scope:** 114-200 agent-days plus a 175-279 hour reserve of your time. You keep optional breadth and give up speed.
- **B — Measure capacity first:** no calendar range until real throughput is known. More honest, but you plan blind meanwhile. Not costed in the plan.
- **C — Adopt the named cuts:** 92-163 agent-days, 175-279 reserved hours of your time, 10-19 weeks at 20-25 hours a week. All mandatory proof stays.
**Recommendation:** C. It cuts optional breadth, not safety or proof, and the plan says the range is an estimate, not a date. Cutting agent-tool polish holds up as agents improve; the kept proof work gets more valuable.
**What would change this:** If real task records show the cuts don't save what the plan assumes, or a mandatory proof fails, re-estimate (the plan falls back to A's range).

## 5. Budget for optional speed and test-quality experiments
Status: decided (A)
**What this decides:** How much time goes to optional performance and "mutation testing" (checking whether tests catch deliberately planted bugs) experiments.
**Chosen:** safety fixes first; optional experiments are capped at two worker-days and four of your hours. Running out of budget never turns a check off or counts as a pass.

## 6. Shipping exactly what was tested
Status: decided (A)
**What this decides:** Whether the published package must be the exact bytes that were tested.
**Chosen:** yes. Prove and publish the exact launch package with its full parts list and test receipts. If a version number gets used by a failed attempt, the next try takes a new number and re-runs the affected proof.

## 7. What happens when Forge can't link skills into an agent tool
Status: open (default A)
**What this decides:** Forge keeps one editable copy of each skill and links it into each agent tool's skills folder. When creating that link fails on someone's machine, what should Forge do?
**Why it matters to you:** Copies drift out of date silently; refusals annoy users. This picks which pain you accept.
**Example:** A user on a locked-down Windows laptop runs setup and the link to Cursor's skills folder can't be created. Under A setup stops with a clear message saying what failed and how to fix it. Under B Forge copies the skill files instead and must later detect edits, update and restore them. Under C Forge ships a separate package per tool's marketplace.
**Options:**
- **A — One source, refuse with a clear fix message:** one update path, failures are visible. Some users hit a stop they must fix. Not costed in the plan.
- **B — Fall back to managed copies:** setup always succeeds, but you take on drift detection, updates and restore. Not costed in the plan.
- **C — Separate marketplace packages per tool:** each has its own caching, update and discovery testing. Not costed in the plan.
**Recommendation:** A. No one has measured how often links actually fail, so building a copy system now is speculative. Neutral to agent capability: a clear refusal message is also what an agent needs to fix the problem itself.
**What would change this:** Evidence that a supported tool or common setup can't create the links, plus a tested copy system that keeps copies in sync.

## 8. How many layers of settings Forge stacks
Status: open (default A)
**What this decides:** Settings come from several places that override each other. How many places, and can personal or team settings switch things on automatically?
**Why it matters to you:** More layers means more customization, but also more "why is it doing that?" moments and more privacy rules.
**Example:** You want "always use the strict reviewer on my laptop." Under A Forge stacks four layers: built-in defaults, then the template the project uses, then the project's own config, then options passed on a single run. Your laptop preference is remembered but only takes effect after you approve it and it is written into the project or run config. Under B a personal and team layer would apply it automatically everywhere. Under C only template and project layers exist.
**Options:**
- **A — Four layers, personal preferences need approval:** one predictable merge order with protected safety rules that no layer can override. Personal settings are one step slower. Not costed in the plan.
- **B — Add team and user layers now:** automatic personal/team overrides, but you must design ordering, privacy and migration. Not costed in the plan.
- **C — Template and project only:** simplest, but less customization than you asked for. Not costed in the plan.
**Recommendation:** A. It keeps one predictable path and the protected rules. It holds up as agents improve: an agent can propose the preference edit, and the approval step is a guard worth keeping.
**What would change this:** A real user who needs team or personal overrides to switch on automatically and the time to build ordering and privacy rules properly.

## 9. Updating or restarting blocks while Forge is running
Status: open (default A)
**What this decides:** Can an outside block set itself up and clean up after itself, and can you swap a block while work is in progress?
**Why it matters to you:** Hot-swapping and self-managed setup sound convenient but bring crash, cleanup and half-finished-state problems.
**Example:** You publish a new version of the release-notes advisor mid-session. Under A, Forge uses the new version only after a restart, and an interrupted run either resumes or refuses cleanly. Under B an outside "database connection" block could open its connection at startup and close it at shutdown. Under C Forge would swap the block while a run is using it, moving its state across.
**Options:**
- **A — Restart to update; outside blocks don't own setup:** Forge's built-ins keep managing their own resources. Simple and predictable; outside blocks can't hold connections. Not costed in the plan.
- **B — Let outside blocks set up and shut down:** enables persistent resources, but adds partial-failure and cleanup rules. Not costed in the plan.
- **C — Swap blocks while running:** smoothest, but needs draining, cancelling and state transfer. Not costed in the plan.
**Recommendation:** A. Neither launch demonstration block needs to own a resource. Like decision 1, it limits integrations; revisit together with it. A clean resume-or-refuse rule is a guard that matters more as agents run unattended.
**What would change this:** A block people want that really must hold a persistent connection or resource.

## 10. The first marketplace
Status: open (default A)
**What this decides:** How people find and publish blocks and templates at launch.
**Why it matters to you:** A hosted store means servers, logins, signing and security work for one maintainer; a simple index means less polish.
**Example:** An author publishes "release-notes advisor" to npm and submits it. Under A it appears in a curated list Forge generates, pointing at that exact npm version, and the agent tools' own directories handle distribution. Under B users would install it from a Forge-run service that updates on its own. Under C a company would first run its own private registry.
**Options:**
- **A — Curated list over npm:** documented publish and review steps, no Forge-run service. Less convenient discovery. Not costed in the plan.
- **B — Hosted discovery and install service in 0.1.0:** adds logins, signing, updates and security operations. Not costed in the plan.
- **C — Private or federated registries first:** puts company admin needs ahead of the first public author. Not costed in the plan.
Under every option the publish path and the free open checker (the same tests anyone can run locally or in CI) stay required, and the checker is never paid.
**Recommendation:** A. Submission volume is unknown, so a hosted service is premature. Holds up as agents improve: the checker that tests each exact release becomes more valuable as more blocks are agent-written.
**What would change this:** Submissions or removals outgrow what you can review by hand, or real demand for private company registries.

## 11. The first cloud feature
Status: open (default A)
**What this decides:** After launch (version 0.2), what syncing across devices comes first: backup and notes, the issue tracker itself, or an existing notes vault.
**Why it matters to you:** Syncing the issue tracker across devices means two machines could both try to change the record, which needs careful rules about who is allowed to change it. Notes are lower risk.
**Example:** You work on your desktop and your laptop. Under A, 0.2 gives encrypted backup and restore and syncs selected notes and decisions; claiming the same issue from both machines comes in a later, separately tested step. Under B the shared issue tracker comes first. Under C your notes sync through a vault or cloud folder you already use, and issues stay local.
**Options:**
- **A — Backup plus notes sync first, shared issues later:** useful sooner at lower risk. Not costed in the plan.
- **B — Shared issue tracker first:** needs membership, lock handover, offline refusal and restore rules. Not costed in the plan.
- **C — Use an existing vault for notes:** fastest for vault users, but isn't Forge's own sync. Not costed in the plan.
This assumes the separate default that personal knowledge stays on each device at launch; changing that decision changes this one.
**Recommendation:** A. A local copy never silently becomes the record under any option. Rules about who may change the record get more valuable as more agents on more machines act at once.
**What would change this:** Real demand for working the same issue from two machines first (B), or users who already run a vault (C).

## 12. A visual app and outside-app connections
Status: open (default C)
**What this decides:** Whether Forge gets a visual app or a browser/network connection, and when.
**Why it matters to you:** Forge has no built-in UI by design. An app and a secure network bridge are each a separate product to maintain.
**Example:** Someone wants a dashboard showing running agents and setup. At launch, under every option, Forge offers public local data and change APIs that any separate app can use. Under A you commit to building your own app and a secure bridge next. Under B browser/network access with login and revocation is required at launch. Under C anyone can build clients on the APIs, and your own app waits for real demand, with no promised date.
**Options:**
- **A — APIs now, fund an official app next:** clear plan, but commits your time to an app. Not costed in the plan.
- **B — Network/browser access at launch:** needs login, transport and revocation proof before release. Not costed in the plan.
- **C — APIs now, app only on demand:** least commitment; no official app soon. Not costed in the plan.
**Recommendation:** C. Agents use APIs directly, so a UI is more optional as agents improve; the APIs and their permission rules are what lasts.
**What would change this:** A real user repeatedly needing browser or network access, with time funded to secure it.

## 13. Which community to win first
Status: open (default A)
**What this decides:** Which group of people Forge targets first for adoption.
**Why it matters to you:** Your limited outreach and support time goes to one group first.
**Example:** Under A you court JavaScript/TypeScript developers who build agent tools and keep rewriting the same glue for several tools; one publishes a block others reuse. Under B you court framework and MCP-server maintainers who wrap Forge inside their own projects. Under C you court solo builders who start from ready-made templates.
**Options:**
- **A — Independent JS/TS agent-tool authors:** tests whether outsiders can build useful blocks unassisted and whether others reuse them. Not costed in the plan.
- **B — Framework/MCP maintainers:** a strong distribution channel, but they may only wrap your own blocks. Not costed in the plan.
- **C — Solo template users:** can grow fast, but may not test whether outsiders can author. Not costed in the plan.
None of these are paying customers.
**Recommendation:** A. It directly tests the north-star promise that anyone can add capabilities. Holds up as agents improve, since agents will increasingly be the ones writing those blocks.
**What would change this:** Framework-led users sticking around and publishing better (B), or template users building lasting solutions on their own (C).

## 14. Who pays for hosting
Status: open (default A)
**What this decides:** How Forge covers the cost of anything it hosts centrally (search index, cloud sync, test runners, storage).
**Why it matters to you:** Hosting is the real cash cost. Low revenue is acceptable to you, but a growing bill is not.
**Example:** The public block index gets popular and bandwidth costs rise. Under A the index is a static downloadable file, checks run locally or in the author's own CI, and sponsorships or grants cover shared capacity. Under B you'd offer optional paid managed hosting for compute and storage only, with export and self-hosting kept free. Under C sponsors fund Forge-run index, cloud and runners earlier.
**Options:**
- **A — Host as little as possible, seek sponsors and grants:** smallest bill and duties; less convenience. Not costed in the plan.
- **B — Optional paid hosting to recover costs:** covers bills, but adds billing and customer operations. Not costed in the plan.
- **C — Sponsor-funded hosted services earlier:** needs a named budget, monthly cap, operator, isolation and backup proof first. Not costed in the plan.
No option sells passing checks or ranking, and none launches hosted services in 0.1.0.
**Recommendation:** A. There is no measured bill or sponsor yet. Holds up as agents improve: free, local verification gets more valuable as more code is agent-written.
**What would change this:** Recurring hosting bills exceeding grants and sponsorship (B), or a durable funding and operator commitment (C).
