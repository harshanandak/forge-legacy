# Decisions 42–54 in plain language

## 42. Whether to add a release-automation tool now
Status: open (default C)
**What this decides:** Whether Forge adopts a ready-made tool that bumps version numbers and writes changelogs, or keeps the release process it already has.
**Why it matters to you:** Each new tool adds upkeep. The plan says the current protected publish path stays either way. None of the options removes any release check.
**Example:** You merge five fixes. Under A, Release Please opens a "release 0.1.1" pull request built from your commit messages. Under B, each contributor adds a small note saying "patch" or "minor", and Changesets combines those notes. Under C you keep releasing the way you do today.
**Options:**
- **A — Try Release Please:** versions and changelogs come from commit history automatically. You take on one more tool to maintain. Not costed in the plan. An earlier research report preferred it if a tool is added.
- **B — Try Changesets:** contributors state their version intent explicitly. More ceremony per change. Not costed in the plan.
- **C — Keep the current process:** nothing new to maintain, but releases may stay partly manual. The plan credits no time saved.
**Recommendation:** C. As a solo maintainer with no measured release pain, you don't need it yet. Version-bump tooling is a convenience, so keeping it optional holds up as agents improve.
**What would change this:** Releases start costing you real time, or contributors need to declare version intent.

## 43. How much of Forge's code gets TypeScript types before launch
Status: open (default A)
**What this decides:** Forge stays JavaScript. The question is whether to write precise type definitions only for the parts outside authors call, or for the large internal code too.
**Why it matters to you:** Block authors using TypeScript get autocomplete and early error checks only where types exist. Typing everything adds weeks to the launch path.
**Example:** An author writes a "changelog advisor" block in TypeScript. Under A their editor checks every Forge call they make, but Forge's own internal memory code is still untyped. Under B the internal code is typed too, which the author never sees directly.
**Options:**
- **A — Public surface only:** strict, tested types for what outside authors use, checked against the actual published package. Estimated 9–18 worker-days.
- **B — Type the whole internal codebase too:** more internal safety, plus 20–40 extra worker-days on the launch path. A trial found 5,418 strict-mode errors to clear.
- **C — A, plus one named risky internal module:** a bounded extra. The plan names no module and gives no figure beyond "bounded".
**Recommendation:** A. Authors get the value at the lowest cost, and runtime input checks stay in place. Public type contracts become more useful as agents write more of the blocks, because agents rely on them too.
**What would change this:** Real bugs keep coming from untyped internal code, or the public types can't express what authors need.

## 44. How deeply Forge supports running inside T3 Code
Status: open (default C)
**What this decides:** T3 Code is the desktop app that hosts agents like Codex and Claude. The question is whether Forge certifies that its safety rules are actually enforced inside T3, or only documents how it behaves there.
**Why it matters to you:** You work in T3 every day. Research found many gaps in T3: Codex hook results aren't shown, Pi isn't available as a stock T3 provider, logs get truncated, and OpenCode 2.x is marked broken.
**Example:** Your Forge "no push to master" gate denies an action inside a T3 Codex thread. Under A, Forge has tested that path and can show you the denial with proof. Under C the gate may still fire, but Forge makes no promise that T3 shows it or keeps a durable record, and it advertises no "enforced in T3" badge.
**Options:**
- **A — Certify Codex-direct and Claude-SDK in T3:** you get a real enforcement guarantee in your daily tool. Costs 8–14 agent-days and 4–7 maintainer hours.
- **B — A plus more providers and home setups, plus upstream fixes to T3:** the widest coverage. Not costed in the plan.
- **C — Docs and observation only:** no extra work, and no enforcement guarantee inside T3.
**Recommendation:** C for launch, but revisit soon, because you are the main T3 user. Enforcement guarantees get more valuable as agents act more on their own, so this one shouldn't stay deferred for long.
**What would change this:** You or other users need hard enforcement inside T3, and the budget can cover the proof.

## 45. How often Forge rechecks its knowledge of each agent tool
Status: open (default B)
**What this decides:** Pi, Claude Code, Codex and OpenCode change often. This decides how often Forge reviews whether its integrations still match the current versions.
**Why it matters to you:** If the checks are too rare, a new Codex release can quietly break a Forge hook. If they're too frequent, you spend time on reviews. The plan reserves 1–2 hours a week either way until real upkeep is measured.
**Example:** Codex releases a version that changes how hooks run. Under B, that release triggers a focused recheck before Forge claims support for it, and you can roll back to the last known-good version. Under A you'd also do a weekly sweep of every tool's feeds whether anything changed or not.
**Options:**
- **A — Weekly feed scan plus a monthly review, plus immediate checks on security or failures:** freshest, and the most of your time.
- **B — Recheck on each tool release, plus immediately on security, trust or breakage:** lower effort, with known windows where Forge's knowledge may be stale. No time saving is credited.
- **C — Monthly review, plus immediate checks on security only:** least effort, with longer stale windows.
**Recommendation:** B. It reacts to the events that actually break things. Security and breakage triggers become more important as agents run with less supervision.
**What would change this:** Breakages keep slipping through between releases, which would point to A, or the integrations prove stable, which would allow less.

## 46. What the first version of Forge's notes and knowledge layer includes
Status: open (default A)
**What this decides:** What Forge 0.1.0 ships for remembering things: notes for a repo and for your whole machine, search, decision history and links between items. It also decides whether syncing across devices or sharing with others is in the first release.
**Why it matters to you:** You asked for knowledge that works across repos and across your machine. Cloud sync and sharing is a separate, larger project with security and recovery work.
**Example:** You record "we use Node 24 minimum" in Forge. Under A you can search it from any repo on your laptop and see when and why it was decided, but your desktop can't see it yet. Under C your desktop sees it too, but launch slips.
**Options:**
- **A — Full local knowledge in 0.1.0, cloud backup and sync later:** meets your same-machine goal now. Not separately costed here.
- **B — Repo-level knowledge and a portable format first, machine-wide later:** less work up front, but the launch promise must say plainly that machine-wide is missing. Not costed.
- **C — Cross-device and shared in the first release:** the plan prices later backup at 8–14 agent-days and shared issue tracking at 12–22 agent-days, plus security, membership and recovery work.
**Recommendation:** A. It delivers what you asked for without starting a cloud program. Local, durable knowledge stays useful however capable agents get.
**What would change this:** The local privacy and migration work proves too big, or working on the same issue across devices becomes your top need. Choosing B or C also means revisiting decision 11, which sets when the cloud service arrives.

## 47. How fast to physically reorganize the code into the new structure
Status: open (default A)
**What this decides:** The new design groups Forge into six areas. The question is whether to move files into six folders now, or first put clear front doors on each area and move files only when it's proven safe.
**Why it matters to you:** Mass moves break imports, conflict with open branches and existing tests that check file paths, and give no new capability. Never moving leaves the boundaries unenforced.
**Example:** The memory code currently handles both issue records and notes. Under A you add a "knowledge" entry point that forwards to the existing code, switch callers to it one by one, and move the files once tests prove nothing changed. Under B you move everything on day one and spend the next days fixing broken imports.
**Options:**
- **A — Entry points first, move files only with proof:** low risk, but the folders won't look tidy for a while. Not costed in the plan.
- **B — Move everything first, repair afterwards:** a tidy tree fast, with the highest risk of breakage and merge conflicts. Not costed.
- **C — Never move, just document the areas:** no churn, but nothing stops code from crossing the boundaries. Not costed.
**Recommendation:** A. It keeps working code working. This is a structure question, so stronger agents make B less painful, but not safer.
**What would change this:** Tests show a small all-at-once move is safer for a specific area.

## 48. How smart the "connected knowledge" search is at launch
Status: open (default A)
**What this decides:** When Forge links issues, decisions, notes, pull requests and code locations, does it use simple built-in search and direct links, or add AI meaning-based search or an outside graph database?
**Why it matters to you:** Built-in search needs no extra service and keeps your data local. AI search may find more, but it adds privacy, deletion and dependency work that nobody has measured.
**Example:** You ask "what led to the Node 24 decision?". Under A, Forge returns the decision, the issue it links to and that issue's pull request, up to two steps away. It does not find a note that only uses the words "runtime floor". Under B, an experiment tests whether AI search would catch that note.
**Options:**
- **A — Built-in text search plus links one or two steps out:** works offline with no extra service. Proposed caps include 64 items and 1,200 words of context per answer, not yet measured. Not costed separately.
- **B — Add a costed AI-search experiment, not on by default:** tests whether it's worth it. The plan doesn't give the cost.
- **C — Require an outside graph tool:** a hard dependency, and you still own identity, permissions and freshness. Not costed.
**Recommendation:** A. Agents can already search and reason over links themselves, so heavier built-in "smart search" compensates for weaker agents and should stay optional.
**What would change this:** Real use shows repeated misses that links and text search can't fix.

## 49. What Forge's own contribution to multi-agent workflows should be
Status: open (default A)
**What this decides:** Tools like Agent Companion and LangGraph already chain agents together. The question is what Forge adds on top.
**Why it matters to you:** It decides whether Forge competes with workflow engines or sits above them as the part that checks each step's output.
**Example:** Pi finds a bug and hands its findings to Codex for review. Under A, Forge checks the findings match an agreed format and records them against the issue before Codex starts. Bad or stale output stops the chain. Under B, Forge would build its own scheduler to run the whole chain. Under C, Forge only records evidence and leaves the handoff to other tools.
**Options:**
- **A — Checked handoffs between existing tools:** a clear, testable addition. Research suggests a 3–5 week bounded pilot. The plan says the extra value over existing tools is not yet proven.
- **B — Build a full workflow engine:** duplicates existing tools and needs a separate cost review.
- **C — Record and check evidence only:** the fallback if the pilot shows A adds nothing. Not costed.
**Recommendation:** A, as a pilot with a clear stop rule. Checking another agent's output before the next step acts gains value as agents grow more autonomous.
**What would change this:** A side-by-side test shows no benefit over Companion plus plain instructions.

## 50. Which route to use for the first multi-agent demo
Status: open (default A)
**What this decides:** For the first Pi-then-Codex demo, does Forge drive the steps one at a time itself, or first require Agent Companion's graph runner to wait for Forge's approval before starting the next step?
**Why it matters to you:** Today Companion starts the next step as soon as the previous one says "completed", without waiting for Forge's check. Fixing that couples the demo to a second project. Research also logged Companion failures on October 1: ignored settings, stalls and lost jobs after restarts.
**Example:** Under A, Forge sends one Companion job to Pi, checks and records the result, then sends the Codex job. Under B, you first change Companion so its graph pauses for Forge's approval, then run the whole graph.
**Options:**
- **A — Forge steps through jobs one by one:** proves Forge's part without depending on Companion fixes. It does not certify Companion graphs. Pilot estimate 3–5 weeks.
- **B — Certify Companion's graph mode first:** a stronger demo, but it waits on Companion work. Not costed.
- **C — Use a different named provider:** only if it's simpler with the same check. Not costed.
**Recommendation:** A. It separates Forge's value from provider bugs. An independent gate before the next step matters more, not less, as agents get better.
**What would change this:** Companion ships a tested pause-for-approval hook, or another provider proves cheaper.

## 51. When an in-progress workflow can move between your devices
Status: open (default A)
**What this decides:** Can you share workflow definitions through Git now, and can you pick up a running task on another machine?
**Why it matters to you:** Moving a live task safely needs one place that knows which device holds the task. Otherwise both machines might write at once. Simply syncing the database file is unsafe.
**Example:** You start a review flow on your desktop. Under A, your laptop can pull the same flow definition from Git and run it fresh, but it can't take over the half-finished run. Under B, the laptop takes over and the desktop is locked out of that run.
**Options:**
- **A — Share definitions via Git now, live handover later:** cheap and needs no cloud service. You can't resume across devices yet. Not costed separately.
- **B — Build live handover for launch:** needs a server, device membership, locking out the old device and recovery. Separately costed, but the plan gives no figure.
- **C — Defer both:** less work, but it loses easy sharing that costs little. Not costed.
**Recommendation:** A. Making sure only one device can act on a task at a time becomes more important as agents run unattended across machines, so it's worth building properly later rather than quickly now.
**What would change this:** You have a real, recurring need to continue a live task on another device.

## 52. Which agent tools Forge officially supports at launch
Status: open (default A)
**What this decides:** Confirms the trimmed launch list. Pi, OpenCode and Codex are mandatory. Claude Code and Cursor get a well-supported base with stated gaps. Any tool that speaks the common MCP protocol works generically. Native local knowledge is included.
**Why it matters to you:** Every extra tool you certify is ongoing support work for one maintainer. The trimmed list defers T3 enforcement, a new Hermes package, Vercel and LangGraph certification, and extra Claude/Cursor surfaces.
**Example:** A Hermes user under A can still use Forge's existing skills and CLI, but gets no new native Hermes package. Under B you could restore that one Hermes package, with its own budget and proof.
**Options:**
- **A — The trimmed list:** saves about 30–51 agent-days net, giving a forecast of 92–163 agent-days, or 10–19 weeks at 20–25 hours a week.
- **B — Add back one named tool:** you choose it, with its own budget. The plan doesn't price it.
- **C — Add back wider coverage:** more reach, with a recosted, longer forecast. Not costed.
**Recommendation:** A. It fits one maintainer. Support for more tools is reach, not safety, so it can grow later as demand shows up.
**What would change this:** A real user needs a deferred tool, or a cut turns out to remove something Forge already advertises.

## 53. How a first-time author creates a block
Status: open (default A)
**What this decides:** Whether authors build blocks by asking their existing agent and using Forge's CLI and one config file, or through a step-by-step wizard or a separate app.
**Why it matters to you:** It matches how you already work, by asking an agent to add things. A wizard or app is a second product to build and maintain.
**Example:** Someone wants a "license checker" block. Under A they tell Codex "add a license-checker block", Codex uses the Forge CLI, and they can read every file it generated. Under B, Forge would also offer a terminal Q&A wizard, built only after real authors get stuck.
**Options:**
- **A — Agent plus CLI, one config, readable output files:** the least machinery. The building pieces exist but aren't yet one shipped path. Not costed separately.
- **B — Add a terminal wizard later:** helps humans without an agent, built only after measured failures. Not costed.
- **C — A separate authoring app:** a second product with its own owner and budget. Not costed.
**Recommendation:** A. Wizards make up for weak agents, so they should stay optional as agents improve. Agents can never approve their own trust settings under any option.
**What would change this:** Cold trials show authors repeatedly failing in ways that better error messages and docs can't fix.

## 54. What time promise Forge makes for a new author
Status: open (default A)
**What this decides:** Whether Forge publishes a target like "an outside author adds a working capability in 15 minutes", and how strict that target is.
**Why it matters to you:** A time target makes "easy" testable. No timed run has happened yet, so any number is a goal, not a measured result.
**Example:** A new author installs Forge, reads the public docs and adds a capability. Then it must show up and run in Pi, OpenCode and Codex, and a forbidden call must be refused. Under A the clock stops at 15 minutes, including any fixes, trust prompts or restarts. Under B the target is 20 minutes. Under C you publish the raw times with no target.
**Options:**
- **A — 15-minute target, everything counted, all raw trials published:** ambitious and honest. Smaller targets stay: 5 minutes for a skill, 10 for a simple tool, 3 for a behavior edit.
- **B — Start at 20 minutes and tighten with evidence:** safer to hit. Not costed separately.
- **C — No headline until there are enough trials:** avoids overpromising, but gives less of a story.
**Recommendation:** A, as a public target and not a claim, with B as the fallback if early trials miss. Agents will speed up authoring over time, but the refusals and checks inside the clock must never be skipped to hit the number.
**What would change this:** The first measured trials consistently miss 15 minutes.
