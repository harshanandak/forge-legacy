# Decisions 15-28 in plain language

## 15. Which example "bridge" blocks to build first after launch
Status: open (default A)
**What this decides:** After the launch proof, which worked examples should be built first to show Forge blocks connecting real business data, notes and people? These examples come after 0.1.0. They are not launch work.
**Why it matters to you:** The first examples show outside authors what Forge is for. They also test whether one block can really be reused in a different field.
**Example:** A sales builder has a CRM export and an order export. Under A, one block joins them on a shared key and lists unmatched orders, a second block attaches your saved policy notes explaining each mismatch, and later a third drafts a handoff plan for a person to review. Under B, the first examples would post to Slack or react to events, which needs live sign-in and sending. Under C, you would start with notes plus human review and skip the data join.
**Options:**
- **A — Data join plus notes, then a reviewable handoff:** this tests reuse across fields most directly and has no live side effects. Not costed in the plan.
- **B — Automation and messaging first:** it's closer to what people often ask for, but it needs sign-in, sending and safety work up front. Not costed in the plan.
- **C — Notes plus human review first:** this tests context and approval, but it doesn't test a cross-system data join. Not costed in the plan.
**Recommendation:** A. It's the cheapest real test of "blocks from different fields work together," and the human-review step stays as a guard. The guard becomes more valuable as agents get more capable.
**What would change this:** Real early users who mostly want event or messaging automation.

## 16. How to find out whether people actually use Forge
Status: open (default A, changed from the earlier plan)
**What this decides:** After launch, how much effort goes into recruiting users and measuring whether they keep using Forge?
**Why it matters to you:** You're one maintainer. A large recruitment campaign competes directly with building the product.
**Example:** Three outside authors try Forge after the capability proof passes. Under A, you invite a small group of people who asked for it and publish what happened: who needed help, who reused a block, and who you couldn't follow up with. Under B, you would first need a sponsor, proof of reuse and spare maintainer time, then run a wider outreach program. Under C, you skip cohort work entirely if nobody shows up.
**Options:**
- **A — Small opt-in group of people who asked for it:** you get honest early signal at low effort. The earlier six-week, hundred-activation campaign is deferred. The plan doesn't price it as a separate saving.
- **B — Sponsor-backed wider program:** it reaches more people, but it needs a sponsor and capacity first. Not costed in the plan.
- **C — No cohort unless someone appears:** it costs nothing, and you get almost no usage evidence.
**Recommendation:** A. It fits a solo maintainer and makes no claims about payment, retention or productivity gains. It doesn't depend on how capable agents are.
**What would change this:** People really do keep using it and recruitment proves easy, which points to B.

## 17. Which agent frameworks get a dedicated connector first
Status: open (default A, changed from the earlier plan)
**What this decides:** Besides the agent tools Forge must support (Pi, OpenCode, Codex, plus Claude Code and Cursor), do any agent frameworks get their own dedicated connector at launch?
**Why it matters to you:** Each dedicated connector is one more thing to test and keep working when that framework changes.
**Example:** A developer building a LangGraph agent wants to call Forge's issue tools. Under A, they use Forge's JSON command line or its one generic MCP server (the standard plug-in protocol that most agent tools speak), and that works for any framework. Under B, you would also build and certify a LangGraph-specific node or a Vercel AI SDK wrapper.
**Options:**
- **A — Generic paths only (JSON command line plus one MCP server):** one code path covers every framework. The plan estimates this saves about 2-4 agent-days for Vercel and 1-2 for LangGraph.
- **B — Add one named Vercel or LangGraph connector now:** better reach for that one framework, but it costs that work back plus installed-version testing.
- **C — A different framework's connector, once someone asks for it:** same cost, aimed at real demand.
**Recommendation:** A. As agents get more capable, they handle generic MCP well, so framework-specific wrappers matter less.
**What would change this:** A real user who can't get equivalent results through MCP or the command line.

## 18. How much of running multi-step workflows Forge does itself
Status: open (default A)
**What this decides:** When a user chains steps together ("check, then review, then hand off"), does Forge run the chain itself, or does it hand the plan to the agent tool that's already running?
**Why it matters to you:** A full workflow engine (branching, pausing, resuming after a crash) is a big, separate product. Taking it on would change what Forge is.
**Example:** A user's flow is "run tests, then ask for review." Under A, Forge checks that the chain is valid and passes it to the host (Codex, OpenCode and so on) to run. Forge only runs single quick steps and its own small built-in templates itself. The review step can't start until Forge's issue record has confirmed the test step. An agent saying "done" isn't enough. Under B, Forge would run any branching workflow and survive restarts. Under C, even the built-in templates would rely on the host for ordering.
**Options:**
- **A — Check and hand off; run only simple steps itself:** it reuses what already exists and keeps the confirmation guard. Not costed separately.
- **B — Build a general workflow engine:** it can run any shape of workflow, but it's a large unpriced program.
- **C — Leave all ordering to the host:** less code, but the built-in templates lose their guaranteed order.
**Recommendation:** A. The rule that "the record must confirm a step before the next one starts" becomes more valuable as agents act more on their own.
**What would change this:** A real need that hosts can't meet without losing that guard.

## 19. How much OpenAI-specific support ships at launch
Status: open (default A, changed from the earlier plan)
**What this decides:** Beyond the required Codex support, does Forge also ship examples for the OpenAI Agents SDK or ChatGPT apps (sign-in, cards, extensions)?
**Why it matters to you:** Every extra OpenAI surface adds sign-in, privacy and upkeep work for one maintainer.
**Example:** A user runs Forge inside Codex, and that's fully supported under every option. Someone else wants Forge inside a ChatGPT app with OAuth sign-in. Under A, they would use the generic MCP server and there's no ChatGPT-specific package. Under B, you would build and prove one such package.
**Options:**
- **A — Codex plus common formats and MCP only:** Codex stays required, and the extra SDK and ChatGPT examples are dropped. The plan doesn't put a separate number on this cut.
- **B — Add one named OpenAI SDK or remote surface:** more reach, but it needs sign-in, privacy and maintainer capacity proven first. Not costed in the plan.
- **C — Put all extras on hold indefinitely:** the same as A in practice, just stated as a standing policy.
**Recommendation:** A. A capable agent can use the generic MCP route, so vendor-specific extras can wait for real demand.
**What would change this:** A named user who needs a specific OpenAI SDK or client and has the capacity to support it.

## 20. One source for skills and per-tool files
Status: open (default A)
**What this decides:** Forge's skills and settings files for each agent tool (Claude, Cursor, Codex, Hermes and so on). Are they all generated from one master copy inside the one npm package, or kept as separate hand-maintained copies?
**Why it matters to you:** Separate copies drift apart, and each one needs its own release.
**Example:** You fix a typo in the "review" skill. Under A, you edit it once, and Forge regenerates the Claude, Cursor, Codex and Hermes versions in their own native formats. A drift check catches anyone who hand-edits a generated copy. Under B, you would edit five copies in possibly separate packages. Under C, you would adopt someone else's distribution tool.
**Options:**
- **A — One master copy, generated per tool, one package:** one place to edit, and each tool still gets its native format. Not costed separately.
- **B — Independent copies or packages per tool:** each copy is easier to customise, but you get duplicated work and drift.
- **C — Another distributor:** only worth it if it proves a better fit. Not costed in the plan.
**Recommendation:** A. It matches how this repo already works, and it doesn't depend on how capable agents are.
**What would change this:** Agent tools agree on one shared standard format, which would simplify the generator.

## 21. One small built-in MCP server
Status: open (default A)
**What this decides:** Does Forge ship one built-in MCP server (the standard protocol agent tools use to call outside tools) that exposes issues, recaps, gates, config and memory? Or does that wait?
**Why it matters to you:** MCP is how most agents and frameworks would reach Forge without a dedicated connector. Decisions 17 and 19 assume this server exists.
**Example:** A LangGraph agent wants to claim an issue and post a comment. Under A, it calls Forge's MCP server, which runs the same guarded code as the command line, including permission checks. Under B, it can't do this until 0.2, and the plan's tool claims must be cut back. Under C, it can read issues but can't claim or comment yet.
**Options:**
- **A — Full server now, sharing the command line's code:** one code path, and it's tested against real clients. Not costed separately.
- **B — Defer MCP to 0.2:** less launch work, but the interoperability claims must be withdrawn.
- **C — Read-only first:** lower risk, but agents can't make changes through MCP yet.
**Recommendation:** A. A shared, guarded path for changes matters more as agents act on their own, and it's what makes the "generic route" in decisions 17 and 19 real.
**What would change this:** Real clients that can't keep the permission checks and refusals intact through MCP.

## 22. Making OpenCode support solid before launch
Status: open (default A)
**What this decides:** OpenCode is one of the three agent tools Forge must fully support at launch. How much proof is required before release, and what happens if it fails?
**Why it matters to you:** Your earlier decision made OpenCode mandatory. This decision sets whether "mandatory" really blocks the release.
**Example:** OpenCode's installed version must load Forge's plug-in, block a forbidden action, and clean up afterwards. Under A, you prove that against one exact pinned OpenCode version, plus the version you actually use. The newer interface beyond that stays unclaimed. If the proof fails, the release waits. It can't ship labelled "experimental." Under B, you also prove several OpenCode versions. Under C, you delay launch or downgrade OpenCode's required status.
**Options:**
- **A — Prove one exact version before launch:** you get honest required support. Not costed separately.
- **B — Broader version coverage:** more users covered, at a maintenance cost the plan leaves unpriced.
- **C — Delay launch, or make OpenCode optional:** this is the fallback if the proof can't pass.
**Recommendation:** A. Real, tested blocking of forbidden actions is exactly the kind of guard that matters more as agents get more capable.
**What would change this:** The installed proof fails, or your OpenCode version is incompatible.

## 23. When Forge appears in each agent tool's community directory
Status: open (default A)
**What this decides:** Is getting listed in public plug-in directories (Pi's gallery, Claude, Cursor and Codex directories) part of launch, or does it come later?
**Why it matters to you:** Directory reviews run on other people's schedules. Making them launch requirements puts your release date in their hands.
**Example:** At 0.1.0, a team installs Forge from a local or self-hosted bundle. Under A, the Pi npm package and Pi gallery listing can follow once Pi support is proven, with separate approval to publish, and other directories come later. Under B, launch waits until every directory accepts it. Under C, you ship npm and docs only, and people have to find Forge themselves.
**Options:**
- **A — Bundles now, Pi listing after proof, others later:** you reach native communities without waiting on reviewers. Not costed in the plan.
- **B — All listings required for launch:** the widest discovery, but someone else's review queue sets your release date.
- **C — npm and docs only:** the simplest option, and the least discoverable.
**Recommendation:** A. A listing is marketing, not a safety guarantee, so it shouldn't block release. This doesn't depend on how capable agents are.
**What would change this:** Directories that accept quickly and drive real repeat installs.

## 24. A dedicated Hermes package
Status: open (default C, changed from the earlier plan)
**What this decides:** Should Forge build a new native Python package for the Hermes agent tool, with full enforcement, or keep Hermes's existing level of support?
**Why it matters to you:** Hermes isn't one of the mandatory tools. A native package is a separate Python and operating-system support effort.
**Example:** A Hermes user runs Forge today through the existing skills and command line. Under C, that keeps working unchanged, and nothing new is claimed. Under A, you would build and certify a Python package that runs Forge's gates natively on Linux and Windows. Under B, you would ship a narrower package: skills, MCP and opt-in shell hooks that block when they fail.
**Options:**
- **A — Full native package:** stronger Hermes integration. The plan estimates this costs about 10-16 agent-days and 6-10 maintainer hours.
- **B — Narrower skills/MCP package with opt-in hooks:** partial native support. Not costed in the plan.
- **C — Keep current support, and defer the new package:** this saves that cost and drops no existing behavior.
**Recommendation:** C, until a real Hermes user needs native controls. Enforcement is a guard worth having eventually, but not before anyone asks for it.
**What would change this:** A named Hermes user who needs controls the current path can't give.

## 25. Demos with outside memory tools (Graphiti, Basic Memory, note vaults)
Status: open (default C, changed from the earlier plan)
**What this decides:** Should you spend time now building worked demos that connect Forge's memory to outside knowledge tools? The alternative is to keep Forge's own local memory, add export, and document where those tools could plug in.
**Why it matters to you:** You already decided Graphiti is optional and only ever gets decisions, never code. This decision is about whether to demo it now.
**Example:** A user keeps project notes in an Obsidian-style vault. Under C, Forge stores its decisions locally, can export them, and documents how a vault connector could plug in, but ships no demo. Under A, you would build a decisions-only Graphiti demo plus a vault/Git recipe. Under B, you would build one supported read and export adapter for an existing vault.
**Options:**
- **A — Graphiti and vault demos:** it shows the integrations working. The plan estimates about 4-8 agent-days and 3-5 maintainer hours.
- **B — One supported vault adapter:** a deeper but narrower integration that needs licensing, deletion and conflict handling. Not costed in the plan.
- **C — Local memory, export and documented plug-in points only:** this saves that time, and the outside-tool connections stay less tested.
**Recommendation:** C. Capable agents can work across outside tools themselves, so pre-built demos are optional.
**What would change this:** A real recurring task that Forge's built-in search and links can't handle.

## 26. Keep Forge's PR shepherd or switch to GitHub's merge queue
Status: open (default A)
**What this decides:** Should Forge keep merging PRs one at a time through its own guarded process, or adopt GitHub's merge queue?
**Why it matters to you:** The queue could reduce custom code, but GitHub documents it only for organization-owned repositories. Whether your repo is eligible is unknown.
**Example:** Two PRs are ready together. Under A, Forge merges them one at a time. Before each merge it re-checks the exact commit, the linked issue, who holds the work, and approval. Under C, GitHub's queue would test them together and merge them. Getting into the queue isn't the same as being merged, and Forge's checks of who can merge could be stale by merge time.
**Options:**
- **A — Keep strict one-at-a-time merging; the queue is a later experiment:** all merge guards stay. The plan finds no proven saving from deleting the shepherd.
- **B — Pilot the queue in an eligible organization repo:** you learn whether it works, but only after eligibility and guard checks are proven. Not costed in the plan.
- **C — Make the queue the default now:** the plan recommends against this without those proofs.
**Recommendation:** A. Checking that the right person is allowed to merge exactly this commit is an irreversible-action guard, and it matters more as agents merge on their own.
**What would change this:** Serial merging becomes a measurable bottleneck, and you have an eligible repo with all the guards proven.

## 27. What the getting-started guide leads with
Status: open (default A, changed from the earlier plan)
**What this decides:** What does a new user's first walkthrough show?
**Why it matters to you:** The first page sets what people think Forge is. Keeping three separate polished guides up to date is expensive.
**Example:** A new user opens the quickstart. Under A, they add one capability, change one behavior through config, and watch it take effect in their agent tool. The workflow and agent views reuse that same example. Under B, they start with the PR delivery workflow. Under C, they start from what the agent sees as a tool.
**Options:**
- **A — One "add a capability / change behavior / see it work" walkthrough:** one guide to maintain, and it matches the "build blocks" goal. The plan doesn't price it separately.
- **B — Lead with delivery:** familiar to current users, but it hides that Forge is a platform.
- **C — Lead with the agent-tool view:** good for agent builders, but it means another separately maintained entry point.
**Recommendation:** A. It reflects the platform goal, and it doesn't depend on how capable agents are.
**What would change this:** New users testing the public docs can't follow it.

## 28. How many polished starter templates ship
Status: open (default B, changed from the earlier plan)
**What this decides:** How many ready-made, polished starter templates ship at launch?
**Why it matters to you:** Each polished starter is more docs and support work for one maintainer.
**Example:** A new author wants a starting point. Under B, they get one polished "advisor" starter (data in, advice out, no PR delivery) plus the existing delivery workflow as a reference. The check, review and recovery examples still exist as test fixtures, but not as polished starters. Under A, you would polish three starters in sequence. Under C, the delivery workflow leads, and the advisor proof sits off to the side.
**Options:**
- **A — Three polished starters:** more examples, and more support. The plan doesn't price it separately.
- **B — One polished advisor starter plus the delivery reference:** less to maintain, with all required tests kept.
- **C — Lead with delivery:** familiar, but it hides outside authoring.
**Recommendation:** B. It's consistent with decision 27, and it doesn't depend on how capable agents are.
**What would change this:** Repeated outside requests for more starters, plus the time to support them.
