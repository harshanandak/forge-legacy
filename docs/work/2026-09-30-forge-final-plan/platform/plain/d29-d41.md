# Decisions 29–41 in plain language

## 29. Whether to run a study proving Forge makes people faster
Status: open (default B)
**What this decides:** Should Forge pay for a proper study measuring whether it makes developers or agents more productive, or just keep simple local timing records for now?
**Why it matters to you:** It decides what you can honestly claim at launch. The plan says no "X% faster" claim is justified today. Outside productivity research it looked at is mixed, and none of it measured Forge.
**Example:** A new author adds a "changelog check" block. Under B, Forge records how long that took from a cold start, including failures, repairs, trust prompts and reloads, and keeps the raw records. Under A or C, you would also recruit matched users and compare them with people not using Forge, which needs consent handling and a plan for counting failures.
**Options:**
- **A — Opt-in pilot alongside adoption:** gives early comparison data, but adds collection work nobody has funded. Not costed in the plan.
- **B — Local timings only, study later:** cheap and honest, but gives you no uplift number. A small group of early users after launch only if someone asks for it. The plan says the deferral saves nothing from the base work; the later study is unpriced.
- **C — A formal pre-planned study as its own program:** the strongest evidence, but a separate statistics program after demand exists, and it can never stand in for the safety checks. Not costed in the plan.
**Recommendation:** B. Measuring before anyone uses it is wasted effort. This holds up as agents get more capable, because the timing records stay useful whatever the agent.
**What would change this:** Real, repeated demand plus money set aside for a matched study (publishing negative results too).

## 30. Memory and code-map tools
Status: decided (A)
**What this decides:** Where Forge stores project knowledge, and whether heavy knowledge-graph tools are built in. **Chosen:** local Forge memory for project notes and decisions by default. Graphiti is an optional add-on that only gets decisions, never code. Graphify is a separate optional add-on. A built-in JS/TS code map comes only if people actually need one and the Python tools block them.

## 31. Pi's status label and priority
Status: decided (A)
**What this decides:** How Forge labels its Pi integration before it's proven. **Chosen:** Pi is labelled "Experimental" until a test of the installed version, run with no human at the keyboard, passes. It stays the priority, flagship harness.

## 32. What has to pass before Pi gets the "Supported" label
Status: open (default A)
**What this decides:** Which tests must pass before Forge 0.1.0 can call its Pi integration "Supported". Pi support is required for launch.
**Why it matters to you:** No option lets you ship with a failed required harness. The choice is how much testing you do and whether Pi can hold up the launch date.
**Example:** A user installs Forge into Pi 0.99.2 and asks the agent to edit a protected file through a nested tool call. Under A, the release has to show that this exact package installs cleanly, its skills don't load twice, the blocked edit really is blocked (including through nested calls), and cleanup happens. You also run one manual check yourself on Windows in Pi's terminal interface. "It started and exited cleanly" does not count.
**Options:**
- **A — Installed-package tests on the pinned Pi version plus your manual Windows run:** you get a real "Supported" label for that version, and the newest Pi release is only an early warning. The plan estimates 7–10 days for the native Pi work. The packaging, install, cleanup and Windows checks haven't been run yet.
- **B — Hold the launch, labelled Experimental, until the tests pass:** this is honest, but it can delay the launch. Not costed in the plan.
- **C — Also test more providers and interfaces before launch:** you get more coverage and more time. The plan says it would be priced separately.
**Recommendation:** A. It's the smallest test that justifies the label. Checking that a block really is blocked matters more as agents act more on their own.
**What would change this:** Any required check failing. Pi then stays Experimental and the launch waits until it's fixed.

## 33. Programming language and whether Forge runs a permanent background process
Status: open (default C)
**What this decides:** Whether Forge stays a JavaScript command-line tool that runs only when called, or adds a background process that stays running (possibly written in Rust).
**Why it matters to you:** A background process adds start, stop, crash and cleanup work. Rewriting in another language doesn't fix memory use. The plan's measurements found a sample command used about 75 MB on Node and 51 MB on Bun. They also found that one Forge server per session at 20 sessions could approach 1.5 GB. Those are rough estimates, not measured savings.
**Example:** You have 20 agent sessions open across ten projects. Under C, nothing from Forge runs between commands: each command starts, does its work and exits. Under A or B, a shared background service would keep data in sync and answer every session, which needs locking down, cleanup and restart handling.
**Options:**
- **A — Stay in JavaScript and measure a shared background service first:** adds a long-running service before there's a proven need. Not costed in the plan.
- **B — Price a Rust background service for comparison:** the plan estimates a Rust comparison at 12–21 days (10–16 hours) if it's ever needed.
- **C — JavaScript, on demand only, with strict public types and real-workload measurements:** always-on sync is deferred, along with an unadvertised compiled-Bun experiment. The plan says deferring that experiment saves 2–4 days.
**Recommendation:** C. There's no measured bottleneck yet. Running only on demand holds up as agents get more capable.
**What would change this:** Real measurements showing sustained memory or speed problems (the plan sets triggers, such as a shared service over 128 MB when idle), or users needing live sync across sessions.

## 34. How Forge uses your Agent Companion handoff tool
Status: decided (A)
**What this decides:** Whether the owner's Agent Companion handoff tool becomes part of Forge core. **Chosen:** it stays outside Forge as an optional, separately approved add-on block that runs work. Forge doesn't embed its routing code and doesn't build its own session runner.

## 35. Whether Forge setup still writes a CLAUDE.md file
Status: open (default A)
**What this decides:** When someone sets up Forge in a project used with Claude Code, does Forge still generate a CLAUDE.md file that just points to AGENTS.md?
**Why it matters to you:** Claude Code reads AGENTS.md natively from version 2.1.277, but only when there's no CLAUDE.md file in the folder or any parent folder. A leftover pointer file can quietly stop AGENTS.md from loading that way. The plan notes that the change to remove existing pointer files (PR #605) is still open and unmerged.
**Example:** A user on Claude Code 2.1.280 runs Forge setup. Under A, Forge doesn't write CLAUDE.md and Claude reads AGENTS.md directly. A teammate on an older or unidentified version still gets the pointer file. Under C, that teammate would lose their instructions.
**Options:**
- **A — Check the version:** no file for 2.1.277 and newer, the pointer for older or unknown versions, and users' own files are never touched. Removing an existing pointer happens only when asked. Not costed in the plan.
- **B — Always write the pointer:** safe for old clients, but on new ones it blocks Claude Code from reading AGENTS.md directly. Not costed in the plan.
- **C — Never write the pointer:** simplest, but it breaks older clients. Not costed in the plan.
**Recommendation:** A. This is clean-up for compatibility, so it naturally fades as clients update.
**What would change this:** A real installed test showing the version rule is wrong, or a user who explicitly wants the pointer kept.

## 36. How Forge packages itself for Codex and gets trusted
Status: open (default A)
**What this decides:** How Forge ships its Codex add-ons, and how Codex comes to trust Forge's hooks (scripts that run before or after the agent's actions).
**Why it matters to you:** The plan found that in Codex 0.159.3, if a newer-style plugin file sits at the package root, Codex ignores the older local hook setup. It also doesn't load hooks from that newer file. Ship it the wrong way and Forge's safety hook silently never runs.
**Example:** A user installs Forge for Codex locally. Under A, the package contains two separate bundles: a local one where hooks run after the user approves them through Codex's normal hooks review (Forge also checks the script contents haven't changed), and a portable one for skills and tool servers. Under B, the user gets skills and tools only, and nothing blocks a bad edit.
**Options:**
- **A — Two separate bundles in the one package, with normal trust review:** you get the full current feature set, but two bundles to maintain and test. Not costed in the plan.
- **B — Portable skills and tools only for now:** simpler, but drops the safety hooks. Not costed in the plan.
- **C — Wait until Codex's newer loader supports everything:** the launch then depends on Codex's release schedule. Not costed in the plan.
**Recommendation:** A. The safety hook is exactly what gets more valuable as agents act more on their own. Trusting Forge without anyone at the keyboard is unproven, and the plan rules out faking it.
**What would change this:** Codex's newer loader proven to run the hooks, which would collapse this to one bundle.

## 37. How Pi and OpenCode call into Forge
Status: open (default A)
**What this decides:** Whether Pi and OpenCode reach Forge through small built-in tools in each harness, through a shared MCP server (a standard tool-server protocol), or through the command line.
**Why it matters to you:** It decides how native Forge feels inside each harness, and how many extra processes run.
**Example:** In Pi, an agent asks Forge to claim an issue. Under A, it calls a small Forge tool built into Pi: the request is checked, logged and tied to that session, and it all runs on the same Forge code. A shared MCP server is added only if the user's setup asks for one. Under C, every call starts a new command-line process, which is slower and harder to tie back to the session.
**Options:**
- **A — Built-in tools, optional shared MCP, command line as fallback:** you get native behaviour and one shared implementation, but have to test each harness version separately. Not costed in the plan.
- **B — MCP only:** one route, but adds a server dependency where built-in tools already work. Not costed in the plan.
- **C — Command line only:** you'd have to promise less about the native experience, and every call starts a new process. Not costed in the plan.
**Recommendation:** A. Under every option, a change whose outcome is uncertain is never retried through a different route. That rule matters more as agents grow more autonomous.
**What would change this:** The built-in tool interfaces proving unstable across versions, making MCP the simpler route.

## 38. How much of Cursor to test before launch
Status: open (default B)
**What this decides:** Whether Forge's Cursor support is tested and labelled for the command-line tool only, or for both the CLI and the desktop editor, before launch.
**Why it matters to you:** Cursor must be well supported, but it doesn't block the launch. A passing CLI test can't prove that the desktop editor finds Forge's rules, or that cloud features behave.
**Example:** A user runs Forge with Cursor's CLI and the edit-blocking hook works. Under B, Forge says "CLI supported, desktop not yet tested." Under A, launch waits until the desktop editor also passes its own tests.
**Options:**
- **A — Test the CLI and the desktop editor separately before the full badge:** a complete claim, but more work now. Not costed separately.
- **B — Provisional CLI label with the desktop gap stated:** current behaviour stays, and broader desktop, SDK and cloud testing waits. The plan puts the deferred extra Claude/Cursor scope at 8–13 days (6–9.5 hours).
- **C — Hold off on the new Cursor bundle and promise less:** you risk dropping useful current features. Not costed in the plan.
**Recommendation:** B. It's honest and cheap. Telling people what's tested and what isn't holds up as agents get more capable.
**What would change this:** Real demand for the desktop editor plus access to test it.

## 39. How Forge watches pull requests
Status: open (default A)
**What this decides:** Whether Forge keeps background watchers on your machine that follow every open PR all the time, or checks PR status only when asked or when GitHub sends an event.
**Why it matters to you:** The PR monitoring code is about 10,070 lines. Retiring the local watcher group could remove about 3,800–4,300 lines. Today AGENTS.md tells agents to read check results from the always-on watcher, so A changes how you work. The plan says A is a plan, not permission to delete running watchers now.
**Example:** You have three PRs open. Under C, a background process on your laptop tracks them all continuously and recovers after crashes. Under A, the agent asks for an up-to-date status when it needs one, or reacts to a GitHub event, and Forge keeps the accepted check results as a record.
**Options:**
- **A — Check on demand and keep the records, retiring the watchers safely:** much less code to maintain, but no continuous local updates. The line counts above are the only sizing.
- **B — Keep the watchers as an optional add-on:** keeps the feature, but saves zero lines because it's still in the package. Not costed in the plan.
- **C — Keep the watchers as the default:** today's behaviour, keeping all its upkeep. Not costed in the plan.
**Recommendation:** A. It's the largest clean cut in the plan. Agents that can check for themselves need watching less, while the records of accepted results stay.
**What would change this:** A real launch need for continuous local updates that GitHub events and on-demand checks can't meet.

## 40. When Forge re-runs failed CI checks without asking
Status: open (default A)
**What this decides:** When a required CI check fails, can Forge re-run it automatically, and on what grounds?
**Why it matters to you:** The research found that part of Forge retries any failed required check within a set number of attempts. That conflicts with a stricter rule elsewhere that rejects ordinary failures. Retrying until it goes green can hide real bugs.
**Example:** A test fails on a PR. Under A, Forge re-runs it only if the CI logs show an infrastructure fault such as a runner crash. The re-run is tied to that exact commit and its evidence is recorded. A real test failure goes to you instead. Under C, someone has to diagnose every failure before any re-run.
**Options:**
- **A — One shared rule: re-run only for infrastructure faults, with evidence, otherwise escalate:** you get consistency, but need an accurate list of fault types. Not costed in the plan.
- **B — A separate rule for each part of Forge, all with the same minimum standard:** keeps the existing differences and the upkeep. Not costed in the plan.
- **C — Diagnose before every re-run:** the tightest control, but slower. Not costed in the plan.
**Recommendation:** A. Automatic retries that can't hide real failures become more valuable as agents get more capable.
**What would change this:** The fault list misclassifying real failures, which would point to C.

## 41. Supply-chain security tools versus the minimum Node version
Status: open (default A)
**What this decides:** Whether to raise Forge's minimum Node 24 version so it can use the newest package-signing check tools, or keep the current minimum and use only compatible versions.
**Why it matters to you:** The newest Sigstore signature tools the plan audited require Node 24.15 or later. Raising the minimum could lock out users on earlier 24.x versions. A related CloudEvents library declares support only up to Node 24.
**Example:** A user on Node 24.10 installs Forge. Under A, it installs, and signature checks run in CI or as optional tools. Under B, the install is refused until they upgrade Node. Under C, every install carries the checker whether or not they want it.
**Options:**
- **A — Keep the current Node minimum:** reuses existing CI npm provenance (a signed record of where the package was built) and audit, and adds only tool versions proven compatible. Not costed in the plan.
- **B — Raise the Node 24 minimum:** easier to keep tools current, but changes what Forge supports and needs migration docs. Not costed in the plan.
- **C — Make a current checker mandatory in Forge itself:** stronger by default, but every install pays for it. It needs your explicit approval of its size and support terms. Not costed in the plan.
**Recommendation:** A. Checks that a package is genuine get more valuable as agents install things on their own, but they can live in CI without burdening every user.
**What would change this:** No compatible, maintained checker existing for the current minimum, or users asking for the upgrade.
