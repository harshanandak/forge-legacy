## Blocking issues

### 1. Pre-admission schema processing has no bounded resource contract

**Claim/section.** The author profile is described as bounded; discovery is data-only and precedes admission; config compilation is pure; the normative schema profile admits local `$ref`, `pattern`, asserted formats and `uniqueItems`. See draft:84–90,113–115,148–171 and the contract-lock milestone at 570. [read]

**What is wrong.** Restricting keyword names and avoiding module imports does not bound the work of interpreting outside schemas. A marketplace or independently installed package can supply a permitted regular expression, deeply nested schemas, expensive uniqueness work or a problematic reference graph. The discovery/compiler/validator contract specifies no global schema/config byte or depth ceiling, reference traversal budget, graph size ceiling, or enforceable validation-cost policy. Execution admission occurs later and therefore cannot protect this earlier boundary. This can hang or exhaust the agent-facing CLI/service while merely validating an unfamiliar composition. It is a plan-level safety omission, not a claim that the unimplemented Forge validator has already been exploited. [read: complete draft, especially 165–171,173; inferred]

**Evidence.** JSON Schema's own [security considerations](https://json-schema.org/draft/2020-12/json-schema-validation#name-security-considerations) warn about expensive regular-expression backtracking. Ajv's [untrusted-schema guidance](https://ajv.js.org/security.html#untrusted-schemas) separately identifies schema depth/compilation and validation cost; its [trusted-schema guidance](https://ajv.js.org/security.html#security-risks-of-trusted-schemas) notes that even short strings can trigger expensive regex evaluation. These are mechanism evidence, not a recommendation to adopt Ajv or proof Forge uses it. [external]

A bounded subprocess probe evaluated Node 24.18.0 `new RegExp("^(a+)+$").test("a".repeat(28) + "!")`. The 29-character input exceeded a 500 ms child deadline and returned `ETIMEDOUT` after 515 ms; the launched child was terminated. This proves a cost hazard for a pattern the proposed keyword profile allows. It does not measure a future Forge validator or establish an exact production latency. A `maxLength` alone is consequently insufficient protection. [ran]

**Specific fix.** Before contract lock, specify and test a resource-safe declarative input profile: global bytes/depth/node/reference and instance-size limits, terminating reference/default traversal, bounded uniqueness/format handling, and a regex policy whose enforcement does not depend on an event-loop timer. The smallest default is to omit author `pattern` initially and refuse recursive schema-reference graphs unless bounded traversal is explicitly supported. Bound parsing/compilation as well as runtime instance validation. Add pre-admission hostile-schema cases to G3/G4 and prove typed refusal with no block import, output, side effect or stalled owner service. Keep valid local references and the concrete outside-author journey. [inferred]

**Reasoning and alternatives.** A smaller safe declarative profile protects the boundary without turning trusted block execution into a new sandbox program. Retaining the entire listed profile is acceptable only with a separately supervised or otherwise demonstrably bounded validator and its measured cost; it adds implementation/certification work. Trusting schemas merely because runtime code will later require admission leaves preview exposed; regex heuristics or a same-process timeout are insufficient enforcement. The answer changes if the chosen validator/profile already proves bounded processing for adversarial schemas, with the exact public conformance cases and limits published. [inferred; external/ran evidence above]
