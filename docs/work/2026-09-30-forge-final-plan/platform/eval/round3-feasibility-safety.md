## Blocking issues

### 1. Executable capture is outside the explicit pre-admission resource limits

**Claim/section.** Section 3.1 captures executable bytes and computes identity **before** receiving the affirmative code-admission decision (draft:120). Section 3.3 sets 64 KiB per manifest/schema and 1 MiB aggregate per selected catalog closure, plus separate solution/domain/schema-processing limits (draft:281–301). Section 3.12 also puts source capture in separately authorized lock apply before purpose-bound admission (draft:733). [read]

**What is wrong.** The file ceiling is expressly labelled **Manifest/schema files**; no normative rule applies it to the `.cjs` executable, specifies another executable/aggregate snapshot ceiling, or requires a bounded read/copy while capturing it. A small valid manifest can therefore name a very large ordinary action file and reach capture/hashing before that code is admitted. A no-import sentinel can pass while the host allocates or copies an unbounded file. Authorization to apply a lock does not supply the missing resource bound. The supported trusted-code ceiling explains effects *after* admission; it does not protect this earlier host operation. [read: draft:94–105,120,283–293,733,795,860; inferred]

This is a specific uncovered input class, not a claim that the schema fixes failed or that the unimplemented snapshot loader has already been exploited. If “1 MiB aggregate” is intended to include executable bytes, say that normatively and exercise it; its present table label leaves that essential interpretation unsettled. [read/inferred]

**Evidence.** The proposed reused fingerprint foundation [reads the entire file into memory](https://github.com/harshanandak/forge/blob/7d448ec812ef8639790477af07c3c75962173f8a/lib/forge-lock.js#L66-L91): `resolveLocalSource` checks containment/regular-file status, then `sourceIntegrity` hashes `fs.readFileSync(filePath)`. `classifySource` calls those functions at lines 135–140 without checking file size. The existing regular-file check is useful and should be retained; it is not a byte budget. [read, rung 2]

A transient probe loaded that exact remote module with only `node:fs` replaced by an in-memory test double. Both stat checks reported a regular file of **2,147,483,648 bytes**; `classifySource` still reached a whole-file read sentinel. Assertions verified the sentinel and exactly one read attempt. **No large file was created, allocated or read.** This demonstrates the current helper does not enforce size before its read; it is not an OOM reproduction or a test of a future snapshot loader. [ran, rung 4 for the current helper's decision]

**Specific fix.** Extend the supported outside-source profile to bound the complete captured set, including the action file and declared schema/manifest bytes, before import and before whole-file allocation. The smallest starting rule is to apply the already proposed **1 MiB aggregate catalog-closure ceiling explicitly to these captured outside bytes**, retaining the 64 KiB manifest/schema limits; a different code allowance must be explicit and separately budgeted. Retain real-root/regular-file checks, enforce the observed-byte ceiling during read/copy as well as checking stat size, and clean partial snapshots on refusal. Hash exactly the captured bytes. Return a stable source-limit/refusal diagnostic with no import, invocation or successful receipt. [inferred]

Add G3/G4 capture cases for the byte boundary, one byte over, individually valid files exceeding the aggregate, and growth after the initial stat. Reuse the snapshot/load-race and cleanup corpus already required at draft:795,860. A stat-only check misses growth; unbounded `readFileSync` followed by a length check allocates too early. This is one source-profile rule and a bounded capture path, not a sandbox or new execution engine. [inferred]

**Reasoning / alternatives / reversal condition.** The small bundled-CJS demonstrator and existing closure budget support one conservative shared ceiling; it protects unfamiliar local or installed sources without adding a dependency. Merely requiring operator code trust loses because capture precedes that decision. Streaming without a total budget reduces peak allocation but leaves disk/work unbounded; post-read checks are too late. A separately sized executable allowance is reasonable if a required bundled author fixture exceeds the shared cap and measured capture/storage/cleanup cost supports it. This blocker closes when the profile explicitly includes executable capture and its packed negative cases pass; it is not an argument for dropping outside authors or weakening validation. [read: draft:118,285,570–735; inferred]

## Feasibility and safety assessment

**One owner with agents.** The local staged platform is achievable in principle, not yet demonstrated at the proposed capacity. L3's 109 review threads, at least 111 post-open head updates and 62 visible master-merge commits explain why parallel implementers increase serial review/integration work (L3:6,181,198). Its throughput ranges are expressly judgments, and the CI medians/5.25× Windows ratio are elapsed-job measurements rather than owner effort or a proven identity-call cause (L3:190–204; draft:894). V3 correctly substitutes an owner/access ledger, records unknown access as NO, and bars endorsed dates or broad coupled fan-out until measured demand fits committed time (draft:900–906). The illustrative **120–180 owner-hours** is arithmetic supply, not priced demand. The plan requires permitted native operators and a durable observer alongside the landing owner; it does not show that one person currently has those resources. [read/ran/inferred]

The minimal profile is a sensible reduction: one bundled sync action, exact schemas, explicit service slots, startup substitution, manual installation and an early outside/connected slice. General async services, hosted operations, a native UI and HMR would add owners and proof to the serial path without helping the first demonstrators; they are correctly staged. Expand only when the cold task or actual demand requires it and the new owner/proof/cost is named. This preserves the north star rather than retreating to a configurable fixed workflow. [read: north-star:7–35; draft:99–184,397,755–805; inferred]

**Critical path.** The sequence at draft:805,910 is coherent. The connected non-delivery acceptance/refusal case now occurs before the outside pilot exits; this resolves the previous sequencing concern. Operator commissioning, canonical assets, source admission and the first beta.8/binary-loader rehearsal start early, while full reference migration follows author-contract feedback. Public state/events and local data/consent work remain real 0.1.0 dependencies even though hosted operations and UI are later. Final candidate identity must follow all advertised content, and seven qualifying days cannot be borrowed from preliminary RCs. The two milestone-clarity improvements below refine execution, without replacing that sequence. [read: draft:795–805,827–888,910; inferred]

**Kernel, protected state and merge.** The supported design routes accepted progress through Kernel; pure config validation and host-observed advisory execution do not mint authority. Final-graph validation and per-effect checks are complementary, and required-client refusal cannot be hidden by an author returning substitute output (draft:163–165,265,375–424). The remote owning checks bind protected authorization to actor/path/content/worktree/head and deny consumed or ambiguous authority (protected-state-authority.js:178–243). Merge separately re-fetches mandatory context, re-verifies issue binding/current ownership and gate approval, then requests the expected-head merge (merge.js:1368–1464). The plan's clients must preserve those owners rather than export driver/dependency-injection handles. I found no proposed supported-API escape route in the inspected contract; that safety conclusion remains **unproven below runnable platform conformance**. [read, rung 2; inferred]

**Trust and isolation.** V3 explicitly limits its guard claims to supported owning APIs and cooperative trusted local code. A malicious admitted process can use ambient privileges; a Promise refusal cannot undo effects or detached work. Snapshot loading addresses the supported capture/load race, with a stated same-user tampering limitation. These are honest claims. Hosted target fixtures prove local contract fit, not authenticated network service, tenant containment or remote durability. Actual hosted credentials/filesystem/network restrictions require the separately staged live profile and an operations/security owner. Requiring hostile-code containment for trusted local 0.1.0 would add a different release program; change the profile when adversarial or shared-hosting demand actually requires it. [read: draft:103–122,379,413,503–568,1004; inferred]

**Versioning, compatibility and upgrades.** Package version, author ABI, schema, capability interface, artifact and event/transfer versions are separated. Exact locks, row-specific reader/implementer compatibility, experimental opt-in and recorded-context resume/refusal are workable; exact schema identity is conservative and can reject mathematically compatible mappings without falsely proving them. The plan makes that limitation actionable rather than promising arbitrary schema implication (draft:107–118,297–303,381). It still needs the installed export/assets and actual compatibility table it requires. [read/ran/inferred]

The native beta.5/beta.8 contract covers preservation, separate backup/restore assertions, interruption and return after post-cutover writes. Registry readback confirms beta.8's old workspace/runtime floor is a genuine different origin. The inherited plan expressly makes Node24/26 the targets, so that old floor adds a refusal/preflight case, not a promise to run 0.1.0 on Node22. Unsupported stable/Beads-only inputs remain untouched and runnable; imported historical data remains readable without retaining the importer. Nothing here proves a successful upgrade.
