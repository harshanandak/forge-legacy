## B. Solo-maintainer release engineering

### Merge queue versus strict up-to-date checks

[external] GitHub's current eligibility is public repositories owned by organizations, or private organization repositories on Enterprise Cloud. Queue CI must listen to `merge_group`; PR/push triggers alone are insufficient. The queue tests a temporary combined head containing the target base and preceding queued changes. [Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).

[ran] An unauthenticated read of `https://api.github.com/repos/harshanandak/forge` using `Invoke-RestMethod` returned `full_name=harshanandak/forge`, `owner.type=User`, `private=false`, `default_branch=master`. [Repository API](https://api.github.com/repos/harshanandak/forge). [inferred] The documented queue feature is therefore unavailable to this repository in its current ownership form; this is an eligibility conclusion, not a settings-page experiment.

[external] Strict required checks demand an up-to-date base and can cause rebuilds after another merge. Loose checks reduce builds but can allow incompatible base changes to surface only after merge. [Protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

[inferred] Recommended personal-repo practice: keep strict checks, serialize merges, and use the already-decided guarded `forge merge --auto` route. Prepare changes concurrently, but refresh the next merge candidate against the new base and re-evaluate exact head/check/review/issue evidence before merging. Do not replace strict protection with a home-built speculative queue for 0.1.0. Moving to an organization solely to save occasional rebuilds adds administration without demonstrated value; revisit a native queue if measured arrival rate and rebase/rebuild waste warrant it.

### RCs and observation windows

[external] Go's release process treats an RC as nearly final bits, raises the bar for changes after it, and uses the calm period for further testing. Its documented production exposure comes from Google's use of development builds; Forge cannot assume that evidence transfers. [Go release cycle](https://go.dev/wiki/Go-Release-Cycle). Apache's usual review/vote window is at least 72 hours, principally to let distributed volunteers participate; it is not a statistical reliability guarantee or a rule governing a solo npm CLI. [Apache release policy](https://www.apache.org/legal/release-policy.html).

[inferred] Propose the following modest policy, explicitly a Forge choice rather than an externally proven optimum:

| Candidate class | Proposed default | Required observation, not merely elapsed time |
| --- | --- | --- |
| First 0.1.0 RC and ordinary compatible changes | 72 hours after candidate publication and successful install verification | Exercise fresh installation/setup, an existing-repository update, representative issue/claim/worktree/validation/guarded-delivery paths, and each promised harness. Retain actual commands, versions, artifact digest and terminal outcomes. |
| Kernel authority, storage/migration, destructive recovery, or major distribution changes | Seven days | Add restart/crash recovery, concurrent-worktree contention, prior-version restore/recovery and data-preservation exercises. |
| Urgent corrective release | Explicitly shortened window | Keep required artifact/platform checks; record why delay increases harm and retain follow-up observation. This is an exceptional owner decision, not an agent gate bypass. |

[inferred] Start the clock only when the installable RC and promised evidence are available. Feature freeze during observation; accepted critical fixes produce a new candidate and reset the affected observation. File P2s under the owner's review policy; if triage shows a P2 violates a release acceptance criterion, correct its priority or change the accepted scope openly. A quiet week without exercised journeys is not additional proof. Evidence basis: [Go change discipline](https://go.dev/wiki/Go-Release-Cycle), [Apache artifact review](https://www.apache.org/legal/release-policy.html).

### Links, copies and distributable artifacts

[external] Vercel's Skills installer uses `.agents/skills` as canonical content, Windows junctions for its link implementation, and a copy fallback when link creation fails. [Installer](https://github.com/vercel-labs/skills/blob/main/src/installer.ts). Git can check a tracked symlink out as a plain file containing its target when `core.symlinks=false`. [Git configuration](https://git-scm.com/docs/git-config#Documentation/git-config.txt-coresymlinks). npm explicitly excludes symbolic links from packages. [npm publish source](https://raw.githubusercontent.com/npm/cli/latest/docs/lib/content/commands/npm-publish.md).

[inferred] The owner-approved links model is workable if its boundaries are explicit:

- **Authoring:** one physical, versioned `.agents/skills` source; no separately maintained mirror.
- **npm transport:** include physical canonical files in `forge-workflow`'s package allowlist. Package/repo readers resolve the installed canonical tree. Do not expect npm to carry harness symlink entries.
- **Local setup:** native discovery first; create links only for clients that need a different directory. Use the existing path/link helpers and verify the link target, discovery and content version. Never silently replace an unowned skill or directory.
- **Windows/update failure:** attempt supported directory links/junctions with an explicit result. Under the decided link-based policy, failure should be visible and actionable; do not inherit an installer's silent copy fallback and call it one source of truth. A copy exception requires an owner decision and tracked provenance/drift checks.
- **Optional marketplace artifacts:** materialize any needed self-contained bundle from the canonical source as a build artifact, not a second editable tree. If that adds distribution complexity without a promised user journey, defer marketplace publication for 0.1.0 and use the single npm setup route.

[external] A report in Anthropic's own issue tracker describes relative skill links becoming dangling after plugin-cache copying. It is a primary user report, **not a reproduced defect or proof of current status** in this leg. [Plugin cache report](https://github.com/anthropics/claude-code/issues/57339). [inferred] Test marketplace/cache installation independently before advertising it. Codex's documented standalone-link support is not evidence about Claude's cached plugin bundles.

[inferred] Minimal acceptance cases for the distribution change: clean tarball install; clone where Git does not materialize tracked links; moved project or linked worktree; repeat setup/update without duplicates; missing/dangling link target; existing user-owned same-name skill; local versus remote worker discovery; selected supported harness versions; cleanup that removes only Forge-owned projections. These are acceptance recommendations, not tests run by this leg. Basis: [Git behavior](https://git-scm.com/docs/git-config#Documentation/git-config.txt-coresymlinks), [npm packaging](https://raw.githubusercontent.com/npm/cli/latest/docs/lib/content/commands/npm-publish.md), [Codex discovery](https://developers.openai.com/codex/skills/), [Cursor remote scope](https://cursor.com/docs/skills).
