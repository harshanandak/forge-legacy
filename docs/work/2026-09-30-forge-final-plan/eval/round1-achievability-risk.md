## Blocking issues

### 1. The recommended calendar is inferred from merge rates rather than the actual resource-constrained critical path

**Claim/section:** draft:6,86,119–130,155–159 and choice 5 at :250. It calls 4–6 weeks credible using 30–40 ordinary slices and 8–12 coupled slices, with 4–6 or 1–2 merges per day. [read / rung 2]

**What is wrong:** both the workload and the coupled throughput are hypotheses. L3 explicitly says its rates are conservative judgments, its sample contains pre-prepared work and narrow repairs/quarantines, and it has no owner active-time or escaped-defect measure. Its historical workflow span excludes pre-start queue time. PR-open-to-merge time is also not engineering effort. None of those measurements supplies the missing effort for public assemblies, config semantics, permission controls, migration proof or release-evidence infrastructure. [read / rung 2: L3:24–29,85,188–192,247–249]

The milestone table also allows scope/package ownership in weeks 1–2 while stating that acceptance lock waits for the delivery foundation; assemblies wait for preservation/package ownership, config waits for the service seam, and harness/migration work waits for those outputs. These dependencies may fit through carefully chosen vertical slices, but the draft does not identify which outputs unlock which lanes. Counting aggregate landing days does not demonstrate that those serial handoffs fit weeks 2–4. [read / rung 2: draft:94,110–116,123–130; inferred dependency analysis]

| Scenario | Ordinary rate | Coupled rate | Landing days for the draft's workload |
| --- | ---: | ---: | ---: |
| Draft arithmetic | 5/day | 1.5/day | 11.3–16.0 |
| Illustrative reduced-capacity case | 3/day | 0.75/day | 20.7–29.3 |

Both rows were calculated as `ordinary/rate + coupled/rate`. The second row is a sensitivity case, **not** a measured rate or a replacement forecast. Neither row allocates authoring effort, operator approvals, live certification, observation or candidate rework; do not add the foundation again if it is already included in the slice inventory. The sensitivity shows why uncertainty can consume the whole window without any dramatic tooling failure. [ran / rung 4: arithmetic calculation; inferred scenario]

**Specific fix:** replace “4–6 weeks is credible” with a provisional/stretch scenario until the following are in the revised plan: a bounded work-package/dependency inventory; which slices already have implementation and need only acceptance; owner availability and active review/landing/operator time; certification capacity; and an explicit candidate-rejection contingency. Count the serialized package/config/generated-file work once. Use the five-ordinary/one-coupled pilot for early calibration, retain L3's ten working days before increasing WIP, and state the date-reforecast checkpoint. Do not require an exhaustive backlog audit or promise a new date unsupported by measurements. [inferred]

### 2. Mandatory release certification has no concrete execution plan under the current tooling

**Claim/section:** draft:12,51,56,115–117,125–127 and :165. It keeps every supported platform/runtime/mode/harness obligation, at least 50 clean pairs and seven exercised days, with most certification machinery placed in weeks 3–4. [read / rung 2]

Current PR and metadata checks cannot satisfy it. Existing binary CI covers compilation broadly but enables smoke only for Linux x64. The live-harness fixture explicitly stops at metadata. Codex's local dispatch policy cannot originate a Claude session; a permitted Claude-origin lane must exist separately. This does **not** prove such a lane or suitable native runners are unavailable; their availability, owner and turnaround are **unknown in the draft**, and therefore cannot support its certification dates. This requires new proof work and access, not a new general CI framework. [inferred]

### 3. Claim reconciliation hides a separate operator approval and a shared-database quiet window

**Claim/section:** draft:41,110–111,115–116,159 and :166. Claim reconciliation is a prerequisite for controls/migration, but there is no explicit distinction between landed repair capability, corpus acceptance and an operator cutover of the live Kernel store. [read / rung 2]

**What is wrong:** the current issue graph makes that distinction material. The open reconciliation parent has two done implementation children. The repair child's final verification comment explicitly says live repair was not executed and remains a later human-gated action. Its done status therefore cannot close a live reconciliation obligation, and its open parent cannot justify rebuilding the repair tool. The readback does not prove whether a later external operator has applied it; current live-store state remains unverified here. [ran / rung 4, record metadata only: V7]

The tool's approval digest covers the complete authority database, not just the selected claim rows. **Any intervening Kernel write invalidates approval.** With workers claiming/commenting/updating issues against the shared authority, a dry-run reviewed by the single owner can become stale before apply. Ordinary parallel execution can therefore repeatedly invalidate this gate; restore also requires all relevant writers fenced and handles closed. That is a shared coordination dependency, not another independently landable PR. [read / rung 2: V8; inferred failure trace]

**Specific fix:** add an explicit acceptance/cutover decision before migration. First recheck the landed implementations against the candidate and a copied/versioned corpus. Define whether release acceptance requires a real operator-store repair or only certified upgrade behavior. If a live repair is required, schedule a short writer-quiescence window, prepare the fixed-time preflight and independently verified backup/restore evidence, obtain separate approval of the exact digest, apply with CAS, then read back all claim projections before resuming writers. Keep the verified restore path and holder-authorized lease handling explicit. General plan approval is not the later digest approval. If live repair is outside release scope, reconcile the dependency and state that boundary without claiming a live cutover occurred. [inferred]
