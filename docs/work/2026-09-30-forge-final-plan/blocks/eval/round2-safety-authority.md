## Compatibility, config and upgrade assessment

**One effective config, with authority outside precedence.** The four layers have a stated low-to-high order, migrated selectors retain explicit argument > environment > project precedence, and already-resolved library inputs do not reread ambient environment (`draft:217`). This preserves a real existing selector contract: Memory currently uses dependency input > environment > config > local default (`lib/memory/router.js:89–114`). The legacy-key union is important because the current graph resolver only applies known sections (`lib/core/runtime-graph.js:972–996`); v2 explicitly inventories other readers before strict unknown-key rejection (`draft:219`). A key the graph ignores is not thereby invalid product configuration. [read, rung 2; inferred]

**Replacement and updates do not silently reuse identity.** A changed implementation/schema requires a complete fresh options object, validation against new defaults and fresh execution consent; old explicit keys are discarded (`draft:229–234,288,301`). Pinned templates keep stable data and externally targeted IDs/meaning across compatible patches; missing pins, renamed targets and unresolved migration conflicts refuse rather than silently selecting current defaults (`draft:294–300`). This is consistent with the earlier old-base/new-base/local-edit model in `docs/work/2026-04-28-skeleton-pivot/template-library-and-merge-flow.md`, “Upgrade And Merge.” The first loader deliberately uses a closed compatibility policy; a generic service/version solver is deferred (`draft:77,122,381`). [read, rung 2; inferred]

**Resume keeps recorded intent and revalidates current authority.** V2 requires the same recorded composition/source/contract/candidate context, current owner checks and new invocation consent. Missing old source or incompatible host context produces explicit restart/reapproval guidance and retains history (`draft:302–303`). Since invocation snapshots are cleaned up, this permits refusal when old bytes cannot be recovered; it does not promise seamless resume or silently execute the latest file. [read/inferred]

**Native restoration remains necessary and unfinished.** The proposed beta.5/beta.8 preservation requirement and unsupported-origin refusal remain at `draft:304,439,463`. Current `upgrade --self-heal` explicitly excludes snapshot/restore (`lib/commands/upgrade.js:38–44`), and its report states full restoration is unimplemented (`lib/upgrade-safety.js:238–242`). **Public entrypoints do not erase existing consumers.** The full inspected root manifest has neither `main` nor `exports`; adding restrictive exports is proposed work, not a shipped boundary. ## Non-blocking improvements

1. **Enumerate fixed obligations separately from supported policy toggles at interface lock.** `draft:226,288,414` protects mandatory obligations, but implementers need the exact applicable set and its policy identity. Current `lib/core/runtime-graph.js:684–716` deliberately permits unlocked rails, including TDD intent and Kernel tracking, to be configured while locked rails remain fixed. Add a small lock table naming fixed checks, policy-controlled checks and permitted selector changes; retain authorized legacy toggles without allowing an extension to disable protected acceptance or merge checks. This clarifies compatibility rather than weakening gates. [read, rung 2; inferred]

2. **Scope writer concurrency guarantees and test the final-check/replace race.** `draft:236,439` requires validation, intervening-edit refusal and a proved platform-safe replacement. Checking bytes and then renaming alone does not establish compare-and-swap: another writer/editor can change the target between those operations. Specify participating supported writers and their serialization/identity protocol; define honest behavior for uncoordinated editor replacement. Add one contention case at that boundary plus crash/restore readback in the existing preservation lane. Atomic visibility, no lost update and backup restoration are separate properties. The plan already labels the writer missing/unpriced, so this is an implementation-lock refinement, not a resurrected blocker or evidence of a new shipped regression. [read: `lib/config-writer.js:56–59`; inferred interleaving]

3. **Define what “optional” means when a selected renderer fails.** `draft:262,269,288` makes a node optional for composition/replacement and returns INCOMPLETE for invalid receipt input. Current SkillRuntime stops on a non-PASS handler result (`lib/flow/src/skill-runtime.js:253–259`); its dependency metadata validation does not supply optional-failure scheduling semantics (`:317–361`). State whether selected presentation failure ends that invocation or is separately reported, and how it affects required workflow evidence. Preserve accepted Kernel outcomes and keep required failures visible; do not silently convert them to PASS. Reuse the existing consumer case, rather than adding a general optional-node scheduler. [read, rung 2; inferred]

4. **Turn the compatibility window into a small executable matrix per promised entry.** `draft:294–305,362–375` already requires this lock; name concrete old caller → new compatible patch, old provider → new host, pinned starter/override, prerelease-host admission and resumed-context refusal cases. Include the documented deep-import disposition and explicit experimental break/migration policy. Test only the named support window and installed consumers; neither the package semver nor a `forgeRange` string establishes provider compatibility. This makes the existing obligation reviewable without expanding to a version solver or general plugin ecosystem. [read: draft and `docs/guides/ENHANCED_ONBOARDING.md:451–454`; inferred]
