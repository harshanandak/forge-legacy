## Cordis: the actual composition contract

### Plugin, context, services, and dependencies

A plugin is a function called with `(ctx, config)`, an object with `apply(ctx, config)`, or a class constructed with those arguments. `ctx.plugin()` mounts an instance and returns its fiber. The declared metadata includes `name`, `Config`, `inject`, `provide`, and `intercept`; these are code-level declarations, not a signed extension manifest or an authorization model. [external] [Upstream plugin types](https://github.com/cordiverse/cordis/blob/f8ea3cd50f1a5724e8e715995bcde131c9c12b2c/packages/core/src/registry.ts#L69-L99), [vendored documented types](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/vendor/cordis/src/registry.ts#L100-L145).

Services are named capabilities addressed through `ctx`, such as `ctx.tools` or `ctx.llm`. A `Service` subclass registers an instance under its service name; TypeScript declaration merging supplies the corresponding static Context type. Consumers depend on the name/interface rather than importing the provider. Registration and removal participate in the provider's lifecycle. [external] [Service tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/docs/cordis-tutorial/03-services.md#provide-a-service), [upstream registration](https://github.com/cordiverse/cordis/blob/f8ea3cd50f1a5724e8e715995bcde131c9c12b2c/packages/core/src/reflect.ts).

`inject` declares **hard runtime service requirements**. Arrays name services; the object form also supplies service intercept configuration. It is not npm dependency resolution or a semver range declaration. A plugin waits in PENDING until its required providers are available, unloads when they disappear, and reloads against replacements. Optional services in the current Harness tutorial are obtained with `ctx.get()` at the use site, rather than an invented `optional: true` injection syntax. [external] [Inject resolution](https://github.com/cordiverse/cordis/blob/f8ea3cd50f1a5724e8e715995bcde131c9c12b2c/packages/core/src/registry.ts#L11-L58), [dependency lifecycle and optional services](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/docs/cordis-tutorial/03-services.md#consume-a-service-with-inject).

**Operational limit:** a missing provider can leave a composition silently pending; a pending fiber alone need not keep Node alive. The tutorial explicitly documents a zero exit with nothing activated. Dependency-driven loading needs a separate readiness audit and useful missing-service diagnostics. [external] [Missing-provider behavior](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/docs/cordis-tutorial/03-services.md#consume-a-service-with-inject); [inferred] Forge implication.

### Lifecycle, disposal, and the meaning of revert

The fiber tracks PENDING, LOADING, ACTIVE, FAILED, UNLOADING and DISPOSED states. Child plugins and framework registrations belong to their owning context/fiber. For unmanaged resources—timers, watchers, sockets—`ctx.effect()` runs setup and collects its returned disposer. `fiber.dispose()` settles after asynchronous cleanup and child disposal. A cleanup guarantee therefore depends on resources being registered as effects. [external] [Lifecycle tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/docs/cordis-tutorial/02-lifecycle-and-effects.md), [upstream fiber](https://github.com/cordiverse/cordis/blob/f8ea3cd50f1a5724e8e715995bcde131c9c12b2c/packages/core/src/fiber.ts).

“Revert” is the disposal of owned runtime effects, not a general rollback of everything a plugin did. Removing a registered tool or closing a socket can be owned; undoing a Git push, sent message, database commit, or arbitrary import-time mutation requires a separate application protocol. Arbitrary detached work can outlive its intended owner unless explicitly managed. [inferred] Consequence of the effect contract and [external] [Harness safety notice](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/SAFETY.md).

### Configuration and schema

The runtime `Config` export is a Standard Schema validator, alongside an optional TypeScript type of the same name. Schema validation precedes activation; defaults and transformed values are passed to the plugin. Current upstream `resolveConfig()` explicitly rejects asynchronous validators. Schema interoperability is therefore not a promise that every validator execution mode works. [external] [Validation source](https://github.com/cordiverse/cordis/blob/f8ea3cd50f1a5724e8e715995bcde131c9c12b2c/packages/core/src/fiber.ts#L34-L45).

Harness uses its Schemastery fork. Its Loader additionally supports computed `!!js` values and volatile schema fields: validated volatile-only edits update stable references without remounting; ordinary-field edits retain the normal update lifecycle. Those are **documented Harness/Loader mechanisms**, not assumptions about every Cordis embedding. The schema still cannot validate an unavailable resource merely because its name is a string; the plugin must check that reference. [external] [Config tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/docs/cordis-tutorial/05-config.md).

### Composition, hot reload, and isolation limits

Groups compose child plugin entries. Service `isolate` gives a subtree a different instance of a named service; upstream reflection maps service names through context-specific symbols. This allows two groups to use different shell providers without a name collision. It establishes a service-resolution realm, not a process, memory, filesystem, network, or permission boundary. [external] [Composition tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/docs/cordis-tutorial/06-composition-and-hmr.md), [isolation implementation](https://github.com/cordiverse/cordis/blob/f8ea3cd50f1a5724e8e715995bcde131c9c12b2c/packages/core/src/reflect.ts); [inferred] security boundary assessment.

|---|---|---|
| Current upstream Cordis code HMR | Replaces affected plugin fibers; failure handling explicitly leaves a failed replacement registered for a later retry, without rollback. [external] [Source](https://github.com/cordiverse/cordis/blob/f8ea3cd50f1a5724e8e715995bcde131c9c12b2c/packages/hmr/src/index.ts#L445-L465). | Owned teardown is not last-good restoration. [inferred] |

[inferred] |

This is a concrete host-maintenance cost behind an apparently small plugin interface. ### Discovery, compatibility, trust, and config limits

Current Plugin Manager inspects registry packages, local paths, Git addresses and tarballs, installs through pnpm into profiles, and activates selected bundles/rows. It separates package operations from queued config application. Build-script permission and runtime version admission are distinct decisions; already-permitted install-script effects can survive a failed installation. [external] [Plugin Manager](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/boot/plugin-manager/README.md).

Current launcher checks declared `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` peer ranges against its runtime version before importing rows it owns. Missing peers impose no requirement. An incompatible row is denied unless an exact plugin-version/runtime-version exemption exists; direct plugin mounts by another embedder are outside these composition boundaries. This is an admission rule, not a complete behavioral compatibility test or malicious-code sandbox. [external] [Peer-check implementation](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/boot/app-boot/src/plugin-compatibility.ts), [admission boundaries](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/boot/app-boot/README.md#profiles).

## Five comparable extensible systems

These were selected for distinct relevant mechanisms: declarative discovery/activation, capability ownership, cheap functional hooks, configuration-derived workflow graphs, and mature dynamic service compatibility. No marketplace success metrics or measured outage rates are inferred from documentation. [inferred] Selection rationale.

### VS Code extensions

- **Granularity and contract:** one extension can contribute commands, languages, views, debuggers, settings and providers. `package.json` declares identity/version, `engines.vscode`, executable entry, contribution points, activation events and extension dependencies. Settings contributions describe types/defaults and validation metadata; registration APIs return disposables. Manifest dependency IDs do not constitute Cordis-style typed service requirements. [external] [Manifest](https://code.visualstudio.com/api/references/extension-manifest), [settings contributions](https://code.visualstudio.com/api/references/contribution-points#contributes.configuration), [registration return types](https://github.com/microsoft/vscode/blob/main/src/vscode-dts/vscode.d.ts#L10990).
- **Composition and activation:** contribution metadata can be available before runtime activation. Events such as language use, commands and startup completion activate code when needed; some contributions now imply activation without redundant explicit events. [external] [Activation events](https://code.visualstudio.com/api/references/activation-events).
- **Versioning and staging:** the host range selects compatible VS Code versions; proposed APIs are deliberately unstable and restricted to experimentation before stable publication. Microsoft explicitly explains that an API becomes difficult to change once published. [external] [Proposed API policy](https://code.visualstudio.com/api/advanced-topics/using-proposed-api).
- **Discovery and trust:** Marketplace and VSIX distribution, publisher trust, signing/scanning and blocklists provide supply-chain controls. Extensions still run with the extension host's host-user permissions, including files, network and processes. Publisher identity is not a per-capability sandbox. [external] [Marketplace](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace), [runtime security](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security).
- **What became costly at scale:** immutable public API obligations restrict host evolution; malicious extensions require continuing review, detection and removal. Microsoft describes Marketplace protections as a continuing layered process, not a solved trust problem. [external] [API policy](https://code.visualstudio.com/api/advanced-topics/using-proposed-api), [Microsoft Marketplace security account](https://devblogs.microsoft.com/blog/security-and-trust-in-visual-studio-marketplace).
- **Transfer:** publish declarative metadata and activation reasons before inventing unrestricted access to the whole runtime; incubate new APIs outside the stable surface. [inferred]

### Backstage plugins and the new backend system

- **Granularity and contract:** a backend plugin owns a feature; a module extends one plugin in the same backend instance. Modules use named, typed extension points exported from a library boundary rather than depending directly on the implementation package. Modules finish initialization before the target plugin initializes; extension points are initialization-time APIs, not arbitrary live mutation APIs. [external] [Modules](https://backstage.io/docs/backend-system/architecture/modules/), [extension points](https://backstage.io/docs/backend-system/architecture/extension-points/).
- **Provides/requires and schema:** typed service refs, service factories and declared `deps` supply DI; services have root/plugin scope. Plugin packages expose `configSchema`, collected from dependencies as JSON or TypeScript schema definitions. Backend/secret/frontend visibility markers control config exposure. [external] [Services](https://backstage.io/docs/backend-system/architecture/services/), [configuration schema](https://backstage.io/docs/conf/defining/).
- **Versioning and staging:** npm package semver is distinct from Backstage release versions. Export stages (`@alpha`, `@beta`, `@public`) and corresponding subpaths separate unstable from stable APIs; stable breaking changes have a deprecation and upgrade policy. [external] [Versioning policy](https://backstage.io/docs/overview/versioning-policy/).
- **Discovery and trust:** Plugin Directory/community packages are installed as npm dependencies and wired into the app. Backstage's threat model explicitly treats builders/operators as trusted and requires vetting plugins like other external packages; it does not sandbox them. [external] [Discovery](https://backstage.io/docs/getting-started/configure-app-with-plugins/), [threat model](https://backstage.io/docs/overview/threat-model/).
- **What became costly at scale:** manually assembled backend dependency wiring became difficult to evolve. The new system reduced it, but required compatibility wrappers, migration of shared services/authentication and eventual retirement of old entry points. Backend HMR was also dropped. This is documented migration cost, not an invented fleet-outage statistic. [external] [Migration guide](https://backstage.io/docs/backend-system/building-backends/migrating/).
- **Transfer:** expose an owner-specific extension point smaller than the owner's whole service, and use startup composition unless live replacement has a demonstrated need. [inferred]

### Vite / Rollup plugin hooks

- **Granularity and contract:** a plugin is a JavaScript object, usually returned by a factory, with a name and optional hooks. Resolution/load/transform/build/output hooks define different phases; Rollup documents first-result, sequential and parallel dispatch and hook-level ordering. This is a deliberately small executable contract, not a manifest with mandatory provides/requires or a universal config schema. [external] [Rollup plugin development](https://rollupjs.org/plugin-development/).
- **Config-driven composition:** explicit `plugins` arrays select instances; Vite adds `config`, `configResolved`, dev-server/HMR hooks and `enforce`/`apply` controls. Plugin option schemas remain author-specific. [external] [Vite plugin API](https://vite.dev/guide/api-plugin.html).
- **Versioning and compatibility:** plugin npm versions/host dependencies alone are insufficient. A plugin relying on output-phase behavior or `moduleParsed` is not automatically usable in Vite's unbundled development server. Current Vite docs also distinguish Rolldown-powered hosts; the Vite 8 migration changes bundle mutation/reference behavior and parallel-hook execution. [external] [Compatibility conditions](https://vite.dev/guide/api-plugin.html#rolldown-plugin-compatibility), [migration guide](https://vite.dev/guide/migration.html#advanced).
- **Discovery and trust:** ordinary npm package distribution and curated ecosystem lists feed explicit imports in executable config. Code runs as part of the build/dev process; these APIs provide no documented per-plugin permission admission. This is source-level assessment, not a security test. [external] [Conventions and composition](https://vite.dev/guide/api-plugin.html#conventions); [inferred] trust boundary.
- **What became costly at scale:** cross-host and dev/build differences created behavioral compatibility obligations even when hook names matched. Moving the underlying bundler required migration rules for previously usable behavior. [external] [Current migration](https://vite.dev/guide/migration.html).
- **Transfer:** hook dispatch semantics, order, cancellation, error propagation and environment applicability are part of the public contract; they need to be specified before promising that hooks are interchangeable. [inferred]

### Nx plugins

- **Granularity and contract:** plugins contribute project graph nodes/dependencies, inferred tasks, generators, executors and migrations. `createNodesV2`/`createNodes` and `createDependencies` extend graph construction; executor/generator metadata points to implementations and JSON option schemas. Requires are package/API dependencies plus the graph/task relationships emitted by the plugin, rather than a general service registry. [external] [Plugin model](https://nx.dev/docs/concepts/nx-plugins), [graph hooks](https://nx.dev/docs/extending-nx/project-graph-plugins), [executor schemas](https://nx.dev/docs/extending-nx/local-executors), [generators](https://nx.dev/docs/extending-nx/local-generators).
- **Config-driven composition:** `nx.json.plugins` names installed modules with options and include/exclude globs controlling inference. Project configuration can override inferred values. A plugin can add a toolchain to many projects without copying its setup into each one. [external] [Plugin config](https://nx.dev/docs/reference/nx-json#plugins), [mental model](https://nx.dev/docs/concepts/mental-model).
- **Versioning and compatibility:** the create-nodes APIs have an explicit version matrix. For Nx 21 onward the current recommendation exports both names using the v2 implementation; earlier supported hosts need different handling. This is a real compatibility burden beyond package semver. [external] [Compatibility matrix](https://nx.dev/docs/kb/createnodes-compatibility).
- **Discovery and trust:** first-party/community npm plugins and workspace-local plugins share the development surface; local generators give a path to prove internal conventions before distributing them. Installation remains a package supply-chain decision. [external] [Plugin model](https://nx.dev/docs/concepts/nx-plugins), [local generators](https://nx.dev/docs/extending-nx/local-generators).
- **What went wrong at scale:** Nx's September 5, 2025 postmortem records malicious packages published after a GitHub Actions injection stole a publishing token, exposing users through installed packages. Separately, graph-hook API changes required author migrations. Supply-chain compromise and API evolution are different costs and require different controls. [external] [First-party incident postmortem](https://nx.dev/blog/s1ngularity-postmortem), [API matrix](https://nx.dev/docs/kb/createnodes-compatibility).
- **Transfer:** composition should produce inspectable graphs/derived config and preserve inputs needed for caching or affected-work calculations; a plugin name in a registry is not evidence of trust. [inferred]

### OSGi bundles and dynamic service registries

- **Granularity and contract:** a bundle is a lifecycle/module unit; a service is a separately registered capability. Bundle manifests declare identity/version, package imports/exports and capabilities/requirements. Declarative Services metadata describes implementations, provided interfaces, references, cardinality and binding policy. Config Admin/Metatype provide configuration identities and attribute definitions, including types/defaults/cardinality. [external] [Module specification](https://docs.osgi.org/specification/osgi.core/8.0.0/framework.module.html), [Declarative Services](https://docs.osgi.org/specification/osgi.cmpn/8.0.0/service.component.html), [Metatype](https://docs.osgi.org/specification/osgi.cmpn/8.0.0/service.metatype.html).
- **Lifecycle and compatibility:** static references can require restart on provider change; dynamic references support bind/unbind replacement. Implementers and consumers have different safe version ranges: adding an interface obligation can be compatible for a caller while breaking an implementation. [external] [Bound service replacement](https://docs.osgi.org/specification/osgi.cmpn/8.0.0/service.component.html#service.component-bound.service.replacement), [semantic-version roles](https://docs.osgi.org/whitepaper/semantic-versioning/040-semantic-versions.html).
- **Discovery and trust:** repository resources advertise requirements/capabilities and content locations/digests; the resolver finds providers. Signing and security policies are separate mechanisms, and the presence of a repository resource does not itself grant permission. [external] [Repository specification](https://docs.osgi.org/specification/osgi.cmpn/8.0.0/service.repository.html), [security specification](https://docs.osgi.org/specification/osgi.core/8.0.0/framework.security.html).
- **What became costly at scale:** the specification documents split-package completeness, ordering, performance and debugging hazards from `Require-Bundle`, and recommends weaker coupling through package imports. Felix's resolver issue records repeated calculation of transitive `uses` constraints as a time-consuming operation. These are documented structural/scaling pathologies; no fleet incident rate was verified. [external] [Require-Bundle issues](https://docs.osgi.org/specification/osgi.core/8.0.0/framework.module.html#framework.module.requirebundle), [Felix resolver issue](https://issues.apache.org/jira/browse/FELIX-2737).
- **Transfer:** borrow explicit capability requirements, lifecycle ownership and provider compatibility; avoid introducing a general-purpose resolver/class-space framework into Forge merely to load a few modules. [inferred]

### What makes a new block cheap

| Lesson | Evidence | Bounded Forge adaptation |
|---|---|---|
| Depend on a capability, not its provider. | Cordis named services and Backstage typed service refs. [external] [Modules](https://backstage.io/docs/backend-system/architecture/modules/), [hook API](https://rollupjs.org/plugin-development/). | A GitHub provider need not become a new top-level block if an existing adapter contract covers it. A new capability needs a deliberate contract decision. [inferred] |
| Separate discovery metadata from execution. | VS Code contribution/activation separation; Harness checks peers before importing owned rows. [external] [Activation](https://code.visualstudio.com/api/references/activation-events), [compatibility source](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/boot/app-boot/src/plugin-compatibility.ts). | Parse data-only identity, requirements and schema references before trusted activation. [external] [Layer preview](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/boot/app-boot/README.md#previewing-the-effective-configuration), [Nx config](https://nx.dev/docs/reference/nx-json#plugins). | One resolver emits effective config, origins and activation diagnostics; owners consume that result instead of each re-merging config. ### What turns a public API into a maintenance trap

1. **Publishing implementation details as convenient extension access.** Stable public APIs constrain future implementation changes; broad implementation coupling also makes refactoring dependency composition harder. Keep implementation paths private and expose named, small contracts. [external] [VS Code policy](https://code.visualstudio.com/api/advanced-topics/using-proposed-api), [OSGi weaker-coupling recommendation](https://docs.osgi.org/specification/osgi.core/8.0.0/framework.module.html#framework.module.requirebundle); [inferred] adaptation.
2. **Specifying signatures while leaving behavior implicit.** Hook order, parallelism, dev/build availability, error semantics and provider replacement become user dependencies. Vite's current migration demonstrates how changes underneath the same broad plugin model still require compatibility work. [external] [Vite migration](https://vite.dev/guide/migration.html); [inferred] failure mechanism.
3. **Calling semver sufficient without testing implementations.** A caller and a provider can have different compatibility requirements; Nx's hook-name matrix and Harness's missing-peer behavior expose the limits of version declarations. [external] [OSGi roles](https://docs.osgi.org/whitepaper/semantic-versioning/040-semantic-versions.html), [Nx matrix](https://nx.dev/docs/kb/createnodes-compatibility), [Harness peer evaluator](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/boot/app-boot/src/plugin-compatibility.ts); [inferred] requirement for conformance checks.
4. **Promising hot-swap safety before defining the failure boundary.** Cordis upstream, Harness code replacement and Harness config reload have different recovery semantics. General rollback requires more than disposing registrations; external effects and failed restoration remain. [external] [Cordis HMR](https://github.com/cordiverse/cordis/blob/f8ea3cd50f1a5724e8e715995bcde131c9c12b2c/packages/hmr/src/index.ts#L445-L465), [Harness reload matrix](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/boot/app-boot/README.md#startup-and-reload-failures); [inferred] design consequence.
5. **Mistaking discovery for trust.** Marketplace reputation, npm names, compatibility checks and content hashes answer different questions. VS Code documents host-level extension permissions; Backstage explicitly trusts builders; Nx experienced a publishing-chain compromise. [external] [VS Code permissions](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security), [Backstage model](https://backstage.io/docs/overview/threat-model/), [Nx postmortem](https://nx.dev/blog/s1ngularity-postmortem); [inferred] trust separation.
6. **Treating configuration keys and entry IDs as disposable internals.** Once third-party patches target IDs or schemas drive integrations, changing them is another API migration. Harness's whole-config replacement makes retained fields and precedence especially consequential. [external] [Harness layer contract](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/boot/app-boot/README.md#known-limitations-and-deferred-work); [inferred] compatibility obligation.

### How to stage internal blocks into public extensions

The strongest sources support an **incubation and promotion** approach rather than immediately freezing every internal module: VS Code proposes APIs before stability; Backstage uses explicit export stages, invited plugin builders into an alpha before recommending production deployment, and supplied migration wrappers; Nx supports local generators/plugins before distribution. They do not establish a universal rule that every system first had only internal plugins. [external] [VS Code proposals](https://code.visualstudio.com/api/advanced-topics/using-proposed-api), [Backstage alpha account](https://backstage.io/blog/2023/02/15/backend-system-alpha/), [Backstage export stages](https://backstage.io/docs/overview/versioning-policy/#release-stages), [Nx local development](https://nx.dev/docs/extending-nx/local-generators).

Recommended sequence, all [inferred] from those sources and the owner's constraints:

| Phase | What to expose | Evidence needed before expanding |
|---|---|---|
| Internal seams | Modules in the one Forge package; capability-owner boundaries and explicit config selection. | Actual consumers, dependency direction, owned cleanup and authority-preserving behavior. |
| Supported local extension | Narrow Contracts/Flow/Memory/Kernel/config-template subpaths; one explicitly trusted out-of-tree provider or extension that uses only those entries. | Clean installed-package consumer, invalid config/dependency/version cases, duplicate registration, lifecycle disposal, and protected-state refusal. |
| Experimental third-party API | Only the additional seam needed by a real consumer, clearly marked unstable; operator-selected package/version, provenance and compatibility declaration. | Independent provider implementations, actionable admission diagnostics, documented upgrade path and failure semantics. |
| Stable extension API | Selected contract exports, schema/entry compatibility policy and deprecation process. | Consumer and implementation conformance across the promised version window; no reliance on private imports. |
| Broader discovery, if demanded | Catalogue/registry integration over the same contracts. | Maintainer ownership for publisher verification, update/revocation response, dependency/install-script trust and support; discovery alone is not the product's safety boundary. |

**Minimal contract checklist, not a new framework specification:** stable extension identity and supported Forge contract range; declared capabilities provided/required; data-only config schema and merge semantics; activation result/readiness diagnostics; owned disposal; explicit permissions/trust mode; error/refusal behavior; conformance evidence. Provider identity and contract version are distinct. Retain the existing Kernel as authority rather than giving plugins writable authority stores or unrestricted hooks around gates. [inferred] Synthesis of Cordis, Backstage, OSGi, VS Code and Nx evidence above.

For adding a block later, the decisive test is: can an installed consumer introduce it through a supported registration/config seam, explain its resolved dependencies, reject invalid composition, dispose it, and exercise it without modifying unrelated owners? If yes, configuration is useful architecture. If it requires new switches across the facade, resolver and each caller, modular files alone have not created an extension contract. [inferred]

Do not require Cordis, a marketplace, live HMR, a universal DI container, or separately published Forge packages to achieve that test. Add each only if an actual use case exceeds the existing seam; preserve the public contract even if the internal loader changes. [inferred] The preceding systems supply mechanisms to adapt, not a mandate to duplicate their frameworks.
